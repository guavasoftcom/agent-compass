# Backend conventions

Project-wide conventions for `backend/` (Spring Boot 4.1, Java 21). Read [../AGENTS.md](../AGENTS.md) for repo-wide context.

## Spring Boot 4 notes

Boot 4 differs from 3.x in ways that bit this project during the upgrade — keep them in mind:

- **Jackson 3** is the default JSON stack (`tools.jackson.*` namespace; `jackson-annotations` stays at `com.fasterxml.jackson.annotation`). Dates serialize as **ISO-8601 strings by default** (`WRITE_DATES_AS_TIMESTAMPS` moved from `SerializationFeature` to `DateTimeFeature` and now defaults to false), so no `spring.jackson.serialization` override is needed for that.
- **Auto-configuration is split into per-technology modules** that are NOT all pulled in transitively. This project explicitly depends on `spring-boot-flyway` (Flyway won't run migrations without it) and the test scope adds `spring-boot-starter-webmvc-test` for the `@WebMvcTest` slice (now in package `org.springframework.boot.webmvc.test.autoconfigure`).
- **Testcontainers 2.x** renamed the Maven artifacts: `org.testcontainers:junit-jupiter` → `testcontainers-junit-jupiter`, `:postgresql` → `testcontainers-postgresql` (Java package names unchanged).
- **`maven-compiler-plugin` is pinned at 3.13.0** on purpose — 3.14+/3.15 regress Lombok+MapStruct multi-round annotation processing and silently drop mapper beans. Don't bump it.

## Module layout

- `otlp/` — the OTLP ingest slice, with its own sub-packages: `otlp/controller` (`OtlpLogController` / `OtlpMetricController` / `OtlpTraceController` accept `application/x-protobuf` on `POST /v1/logs`, `/v1/metrics`, `/v1/traces`), `otlp/mapper` (`OtlpLogMapper` / `OtlpMetricMapper` / `OtlpTraceMapper` — `@Component`s, not MapStruct — translate OTLP proto into `*Entity` rows including the attribute jsonb maps), and `otlp/service` (`OtlpLogService` / `OtlpMetricService` / `OtlpTraceService` write paths).
- `entity/` — JPA entities (`LogRecordEntity`, `MetricPointEntity`, `SpanEntity`). Attribute payloads use `@JdbcTypeCode(SqlTypes.JSON)` with `columnDefinition = "jsonb"` and a `Map<String, Object>` field.
- `repository/` — Spring Data JPA. Cross-row aggregations are native SQL (`@Query(..., nativeQuery = true)`); simple JPQL stays in repositories that don't need jsonb operators or window functions. `SystemRepository` is the exception to the one-repository-per-table shape: it owns no table, extends the bare `Repository<LogRecordEntity, Long>` marker (the entity is only a managed-type anchor for the proxy — no CRUD is exposed), and hosts the `pg_catalog` / `flyway_schema_history` / cross-table queries behind `/api/system`. Keeping it on Spring Data rather than introducing `JdbcTemplate` is deliberate: the backend has exactly one data-access idiom and is worth keeping that way.
- `service/` — `LogService` / `MetricService` / `MetricSeriesService` / `TraceService` / `TraceExplorerService` are `@Transactional(readOnly = true)` and own the parsing/cursor/range logic for dashboard endpoints; `ReportService` renders the markdown report from a Mustache template. The package also holds stateless helpers shared across those services — `PageBounds` (result-size clamping, see Data below), `HistogramBucketing` (bucket-width ladder walk for the Logs and Traces histograms; each page passes its own ladder), `BoundedEditDistance` (near-miss path matching for the report). Reuse them rather than re-extracting a second copy.
- `controller/` — per-domain REST controllers for the React app under `/api`: `LogsController`, `MetricsController`, `SessionController`, `ToolActivityController`, `TracesController`; `ReportController` serves the markdown report; `SystemController` serves the Settings page's operational diagnostics (storage, ingest health, build/schema, effective configuration, retention preview) — the only controller that takes no time window, since its figures describe the database as it stands, and the only one with a write: `DELETE /api/system/telemetry` is the sole endpoint in the application that deletes data. It requires an explicit confirmation phrase re-checked in `SystemService`, and `ApiExceptionHandler` maps the resulting `IllegalArgumentException` to a 400 so a refusal reads as declined rather than failed. `ApiExceptionHandler` (`@RestControllerAdvice`) maps bare-`@RequestParam` `ConstraintViolationException`s to 400 (class-level `@Validated` throws them raw, which would otherwise surface as 500s).
- `validation/` — `@ValidDateRange` + `DateRangeValidator` cap custom `startTimestamp`/`endTimestamp` ranges at 30 days; any param object exposing the pair implements `DateRangeBounds` so the one constraint covers it (`TimeWindowParams` via record accessors, `TraceFilterParams` explicitly).
- `model/` — record DTOs (Lombok `@Data @Builder` on older shapes like `ToolCallCount` / `TraceSummary`); MapStruct mappers in `mapper/` (`spring` component model, `lombok-mapstruct-binding` keeps them compatible) handle entity → DTO mapping for `LogRecord` / `Span` / `EventRow`.
- `config/` — `TuningProperties` (overridable event/attribute/metric names), `TuningPropertyCatalog` (the authored grouping + descriptions + SQL-mirroring classification of all 52 of those properties, behind `/api/system/configuration`; a reflection test fails the build when a property is added without being classified), `OpenApiConfig`, `MustacheConfig`, `SinglePageApplicationConfig`.

## Naming

- **All variables — method parameters, fields, and locals defined inside methods — use full descriptive names.** Never single letters or two-letter abbreviations. Use `anyValue` not `v`, `keyValue` not `kv`, `hexBuilder` not `sb`, `byteValue` not `b`, `request` not `req`. This rule applies to enhanced-for loop variables (`for (byte byteValue : bytes)`), not just declarations.
- Short names are allowed **only** in: lambda parameters, generic type parameters (`T`, `K`, `V`), standard index loops (`i`, `j`, `k`), and `e` in `catch (SomeException e)`.
- Prefer expressive names over abbreviations everywhere else: `throughputBars` over `bars`, `stepDetails` over `details`.

## Java style

- Java 21, `--release 21`. Don't lower the source level.
- Prefer `MediaType.APPLICATION_*` / `APPLICATION_*_VALUE` constants over string literals like `"application/x-protobuf"`.
- **Extract string literals defined inside methods as `private static final String` constants** at the top of the class — format specifiers (`HEX_BYTE_FORMAT = "%02x"`), header names, attribute keys, magic values, etc. Carve-out: one-off `log.*` and exception messages stay inline (extracting them adds noise without payoff).
- **Extract numeric literals defined inside methods as `private static final` constants whenever the number carries domain meaning** — conversion factors (`NANOS_PER_SECOND = 1_000_000_000L`), per-unit counts (`HEX_CHARS_PER_BYTE = 2`), thresholds, timeouts, sizes, ports, retry counts, etc. Small values like `2` are NOT exempt when they mean something specific. Carve-outs (stay inline): `0`/`1`/`-1` as identities, bit masks like `0xff`, generic index/loop arithmetic, test fixture data, and counts that are obvious from immediate context (`new ArrayList<>(events.size())`).
- Records (not Lombok-annotated classes) for new response DTOs; the legacy `@Data @Builder` shape stays for `ToolCallCount`, `TraceSummary`, etc. until they're touched for other reasons.
- Lombok + MapStruct are both on the annotation-processor path; new mappers use `@Mapper(componentModel = "spring")`.
- Checkstyle runs in the `validate` phase and fails the build. Max line length is 140; tabs are forbidden; `NeedBraces` is enforced (every `if`/`else`/`for`/`while` body wrapped, even one-liners).

## Web layer

- **Thin controllers.** Controllers dispatch to services and shape the HTTP response (headers, status, content-type) — no parsing, no cursor math, no validation logic. Validation is declarative: shared query params bind to `@Valid @ModelAttribute` param objects (`TimeWindowParams`, `TraceFilterParams`, …) carrying Bean Validation constraints like `@ValidDateRange`; `ApiExceptionHandler` turns bare-`@RequestParam` constraint violations into 400s. The dual-window endpoints follow a single shape: `if (startTimestamp != null && endTimestamp != null) return service.xxxInRange(start, end); return service.xxx(minutes);`. Mirror this pattern on every new dashboard endpoint so the frontend can always pick either window form.
- Annotate new endpoints with `@Tag` / `@Operation` (and `@ApiResponses` with concrete `@Schema`) so springdoc OpenAPI stays useful for the React client.
- When both Spring's `@RequestBody` and Swagger's `@RequestBody` are needed, import Spring's and fully-qualify Swagger's (it's documentation metadata, used less in code).
- Don't return JPA entities from controllers — map to a record (or the legacy `@Data` DTO) through MapStruct first.
- OTLP ingest controllers consume `application/x-protobuf` and respond with the matching `ExportXxxServiceResponse` protobuf body, returning `400` with a `partialSuccess.errorMessage` set on `InvalidProtocolBufferException`.
- **The backend also serves the SPA.** `SinglePageApplicationConfig` registers a `/**` resource handler over `spring.web.resources.static-locations` (the released image points that at the Vite bundle it copied in beside the jar; a plain `spring-boot:run` keeps the classpath defaults and serves nothing). Unresolved extension-less paths fall back to `index.html` so React Router's history-mode URLs work; paths with a file extension, and anything under the `SERVER_ROUTED_PREFIXES` list, stay 404 rather than answering a missing asset with HTML. **Adding a server-side route outside `/api` means adding its prefix to that list** — otherwise a mistyped URL under it returns the SPA instead of a 404.

## Data

- **Schema lives in Flyway migrations** under `src/main/resources/db/migration/` (`V1__init.sql` is the base, `V2__attribute_indexes.sql` adds the GIN indexes). `spring.jpa.hibernate.ddl-auto=validate` — Hibernate will fail startup if the entity model and DB drift, so every schema change goes through a new `V{n}__*.sql` migration.
- **Attribute payloads stay in `jsonb` columns** (`attributes`, `resource_attributes`, `scope_attributes`, plus `events` on spans); use the existing `@JdbcTypeCode(SqlTypes.JSON)` + `Map<String, Object>` converter pattern rather than flattening into columns. Index containment-style filters with `USING gin (attributes jsonb_path_ops)`.
- **Native SQL** is the norm in repositories — JPQL has no `jsonb_each_text`, `date_bin`, `percentile_cont`, or window-function support, and almost every aggregation needs at least one of them. Always parameterize values with `@Param` (no string concatenation into the query).
- **Range-and-fallback query pattern.** Repositories take an explicit `(Instant start, Instant end)` range; the service resolves the `?minutes=` form into `now - minutes .. now` and calls the same range method (`MetricPointRepository` and `SpanRepository` are fully consolidated this way; `LogRecordRepository` still carries some `aggregateXxx(..., Instant since)` / `aggregateXxxInRange(...)` pairs). Repositories that also serve the grid filters use a single method with `(CAST(:startTimestamp AS timestamptz) IS NULL OR timestamp >= :startTimestamp) AND (... endTimestamp ...)` so empty/one-sided/two-sided bounds all flow through one query.
- **Cumulative-counter deltas are precomputed at ingest.** `claude_code.*` counters (tokens, cost, active time) are cumulative and re-emitted per stream, where a stream's identity is the FULL attribute set (`query_source` / `agent.name` matter). `metric_points.stream_id` is a stored generated md5 of `metric_name` + attributes; `value_delta` is the reset-aware per-row increment, computed per ingest batch by `OtlpMetricService` (backfilled by `V11`). Every token/cost/active-time/session rollup reads `SUM(value_delta)` — never a plain SUM over the raw value columns, a read-time `LAG`, or bucket-`MAX`.
- **`metric_points.session_id` is a stored generated column, not a raw jsonb read.** `V18` materializes `attributes ->> 'session.id'` into a real `text` column (mirroring `V16`/`V17`'s `event_name`/`tool_name` on `log_records`, but for a different reason — `metric_points.attributes` is barely TOASTed, so this isn't a detoast fix). The window-scoped session CTEs in `MetricPointRepository` (`aggregateSessionSummaries`, `aggregateWorstCacheEfficiencySessions`, `aggregateSessionKpis`, `aggregateNewSessionsTrend`, plus the per-session lookups) filter on `metric_name` + `timestamp` and then need `session_id` per matched row; as an expression, that field can't ride in an index, so every row forced a heap-page visit even though the leading filter was already index-covered. `idx_metric_points_session_id_name_ts` (V13, formerly an expression index) and `idx_metric_points_name_ts` (V1, now `INCLUDE (session_id, value_delta, start_timestamp)`) both carry it as a real column so these queries serve as index-only scans. Only the literal `'session.id'` key was migrated — `findTopTokenRows`' `attributes ->> :sessionIdAttribute` stays a bind-param extraction, since `SESSION_ID_ATTRIBUTE` is shared with `SpanRepository` call sites outside this table.
- **Streams are never retired, so "emitted recently" does NOT mean "active recently".** Claude Code's exporter keeps every metric stream it has ever created alive for the life of the process, re-emitting each cumulative counter once a minute at an unchanged value long after the session that produced it ended. Measured on the live database, 98.9% of all `claude_code.cost.usage` / `claude_code.active_time.total` points are such zero-delta re-exports, and sessions two days dead were still emitting them in the current minute. **Any query that decides membership, recency, or "is this thing live" by the presence of a row in a time window is wrong** — it must test `value_delta IS DISTINCT FROM 0` instead. This is distinct from the rollup rule below: `SUM(value_delta)` already gives the right *number* (ghosts contribute 0), which is precisely why the bug hides — the totals look correct while the row set and its timestamps are badly wrong. `MetricPointRepository.aggregateSessionSummaries` / `aggregateSessionKpis` / `aggregateNewSessionsTrend` carry the filter; a session's true start is `MIN(start_timestamp)` (when the stream opened, ~45s before its first emission) and its last activity is the newest timestamp carrying an increment.
- **The retention purge deletes whole sessions, never rows.** `session.id` sits in the `attributes` jsonb of `log_records`, `metric_points`, and `spans` alike (100% coverage on live data), which is what makes this possible: `SystemRepository.DORMANT_SESSION_IDS_SUBQUERY` computes every session whose last activity *anywhere* — logs, tokens, or traces — is older than the cutoff, and every purge query (`purgeLogRecords`/`purgeMetricPoints`/`purgeSpans`, plus `findPurgeEstimates`) gates on that same set. A row-age-only delete would silently split a session straddling the cutoff — its early turns gone, recent ones kept, lifetime cost permanently understated. Measured on the live database: 0 sessions straddle the default 30-day window, 21 straddle a 7-day one, accounting for 604k rows a naive delete would have partially removed. A sessionless row (unobserved on live data but not guaranteed by the schema) falls back to plain `timestamp < cutoff` deletion — the pre-session-gating behavior.
- **Every purge/preview candidate scan also carries a redundant `timestamp < cutoff` (or `start_timestamp`) guard alongside the dormant-session membership check**, purely so the planner can apply it as a leading index-scan restriction before paying for the `IN` lookup or, on `metric_points`, the correlated `EXISTS`. It changes no result — provably so: a session is only dormant once `max(last_seen)` (the max across all three signals' own per-session maxes) is `< cutoff`, so every row belonging to that session in every table already has `timestamp <= that table's own per-session max <= max(last_seen) < cutoff`. `SystemRepository.DORMANT_SESSION_IDS_SUBQUERY`'s javadoc carries the full argument; `SystemService`'s rendered-SQL mirrors (`SESSION_GATED_DELETE_FORMAT`, `METRIC_POINTS_DELETE_FORMAT`, `PURGE_SCRIPT_HEADER`) were updated in lockstep, and `SystemPurgeIntegrationTest`/`SystemQueryIntegrationTest` (22 tests) still pass unchanged, since the row set purge/preview computes is identical — only the plan Postgres picks to get there differs.
- **Inside a purged session, `metric_points` additionally keeps each stream's newest row.** `value_delta` is computed at ingest against the previous row in the same stream and `COALESCE`s to zero when there is none, so even a session judged dormant and eligible for deletion would spike its own counters if it turned out not to be finished after all: `SystemRepository.purgeMetricPoints`'s `EXISTS` clause runs unconditionally, not gated on session dormancy — "no activity anywhere for a full retention window" is strong evidence the process exited (Claude Code re-emits every counter roughly once a minute for its life) but not a proof of it. This is a defensive assumption, not a confirmed mechanism: no concrete way for a purged `session.id` to re-emit has been verified — it is specifically **not** known to be `claude --resume`, which a live-database investigation of `session.count` streams found mints a disjoint, never-before-seen session id for the heartbeat it emits (a genuinely new stream has nothing to protect; what session id ongoing interactive work uses after a real resume is unverified) — but none has been ruled out either, so the marker closes the question rather than trusts the assumption. Costs ~1 row per dormant stream (~2,200 of 2.2M at the live database's default window). The preview's `preservedRows`, the endpoint's DELETE, and the copyable SQL the UI hands the operator all run the identical predicate — a naive delete pasted into psql would corrupt the same data or split a session. `SystemPurgeIntegrationTest` has one test per guarantee: `purgeNeverTouchesASessionThatIsStillActiveInAnySignal` and `purgeGatesOnActivityAcrossAllThreeSignalsNotJustOneTable` for whole-session gating; `purgeKeepsALiveStreamsPredecessorSoTheNextEmissionIsNotASpike` and `purgeStillKeepsAStreamMarkerInsideAFullyDormantSession` for the stream marker — each purges, re-ingests, and asserts the resulting delta is the increment rather than the whole counter.
- **The purge's dormancy window and Claude Code's own `cleanupPeriodDays` are unrelated settings.** `cleanupPeriodDays` (default 30) controls how long Claude Code keeps a session's local transcript resumable on the user's machine; it is never emitted via OTLP, so this application has no way to know it. If an operator sets the dashboard's retention window shorter than their `cleanupPeriodDays`, a session can still be locally resumable in Claude Code after its telemetry — prompt timeline, tool calls, cost breakdown — has already been purged from `log_records` and `spans`. Resuming then shows the conversation continuing normally, but the Sessions/Logs/Traces pages show that session's history as if it only started at the resume point. There is no code-level fix for this — the two settings live in different systems — so the guidance is operational: keep the dashboard's retention window at least as long as `cleanupPeriodDays` if session continuity in the dashboard matters. The purge dialog and README both say so.
- **Planner statistics on this schema are not trustworthy; count exactly.** `pg_class.reltuples` reports `-1` for a freshly migrated `flyway_schema_history`, and `pg_stat_user_tables.n_live_tup` was measured reporting **6** rows for a table holding **19**. `SystemRepository` therefore uses exact `COUNT(*)` everywhere, which costs 250 ms on the 4.6M-row `metric_points` (an index-only scan) — comfortably inside the 15s `statement_timeout`. Don't "optimize" those into estimates. Two related measurements worth not rediscovering: **`received_at` carries no index on any of the three tables**, so `MAX(received_at)` is a 349 ms sequential scan and bounding it by the indexed `timestamp` does *not* help (a 7-day bound covers ~25% of the table and still plans a seq scan) — read it off the newest row by index order instead (`ORDER BY timestamp DESC, id DESC LIMIT 1`, 0.026 ms); and **`COUNT(DISTINCT stream_id)` (668 ms) is the cheap proxy for metric-series cardinality**, where `/api/metrics/catalog`'s `COUNT(DISTINCT attributes)` over the jsonb payload measured 2188 ms for a single 7-day window.
- **`UNION ALL` legs come back in whatever order Postgres likes.** `SystemRepository.findIngestHealth` returned its legs traces-logs-metrics against the live database while a small test container returned them in written order; its trailing `ORDER BY` is load-bearing, not decoration. Any multi-leg query whose row order reaches the UI needs one.
- **Result-size clamps.** `service/PageBounds` is the single shared helper for cursor-limit / offset-page-size clamping and offset arithmetic — `LogService`, `TraceExplorerService`, and `MetricService` all clamp through `PageBounds.clampPageSize` / `PageBounds.computeOffset` against its `MAXIMUM_PAGE_SIZE` (500) ceiling so attacker-chosen sizes can't OOM or overflow the "+1 probe". Belt-and-braces below that, every pooled connection runs with `statement_timeout = 15s` (`hikari.connection-init-sql` in `application.yml`). Point any new list endpoint at `PageBounds` rather than copying the clamp again.
- **Prompt text lives only on log records, and correlates to traces by `trace_id`.** The raw user prompt is the `prompt` attribute of a `user_prompt` log record (`TuningProperties.promptAttribute` / `userPromptEventName`) — no span carries it. Claude Code stamps each of those logs with the `claude_code.interaction` root span's trace id in the top-level `log_records.trace_id` column, which is how `SessionSummary.firstUserPrompt` (per session) and `TraceSummary.firstUserPrompt` (per trace) resolve prompt text; `MetricService.worstCacheEfficiencySessions` reuses the same `LogRecordRepository.aggregateSessionCounts` query (keyed on the ranked session ids) to fill `SessionCacheEfficiency.firstUserPrompt` rather than writing a second aggregation. Whitespace-collapse and the 200-char preview truncation happen **in SQL** so services never hold untruncated prompt bodies. A null prompt is a normal outcome, not an error: the trace may not be rooted in a conversational turn, or prompt-body capture may have been disabled when it was recorded.
- **Only `api_request` log records carry a model.** `tool_result` rows have no `model` attribute at all, so any per-model split over tool calls has to be correlated, not read. `LogRecordRepository.aggregateToolInvocationsByInnerAttributeAndModelInRange` (the `subagent-usage` split) does it with a `LEFT JOIN LATERAL` back to the last `api_request` in the same `session.id` at or before the tool call, excluding rows that carry `agent.name` — those are turns from *inside* a subagent run, which interleave with the dispatching tool call and would otherwise shadow the dispatcher. Unmatched calls bucket under an `unknown` model rather than being dropped. `agent.name` itself is not a subagent identifier: Claude Code collapses project-local agents to `custom`. A dispatch carrying no `subagent_type` anywhere is credited to `TuningProperties.defaultSubagentType` (`general-purpose`) — that is the agent such a dispatch actually runs on, so an `unknown` identifier bucket there was under-reporting a real one (29 of 254 calls on the live database).
- **MCP tool calls are named differently on the two signals that carry them, and both needed fixing.** On `log_records` (`tool_result` / `tool_decision`), `tool_name` is the single constant `mcp_tool` for every server — the real server/tool identity lives in the `tool_parameters` JSON-**string** attribute, under `mcp_server_name` / `mcp_tool_name` (100% coverage on live data). On `spans` (`claude_code.tool`), `tool_name` is instead the prefixed raw form `mcp__<server>__<tool>` — proliferating into 19+ rows per server that need collapsing, the opposite problem. `LogRecordRepository.MCP_AWARE_TOOL_EXPRESSION` splits the log side back out to `mcp:<server>` rows (reused across the 14 log-backed aggregations that group on the tool dimension); `SpanRepository.aggregateToolLatency`/`InRange` collapse the span side with `starts_with()`/`split_part()` (never `LIKE` — a bare `_` is the `LIKE` single-character wildcard, so `LIKE 'mcp__%'` would match "mcp" plus any two characters plus anything). `/api/tool-activity/mcp-usage` and the report's "MCP servers" section deliberately read only the log side: report **log `duration_ms`** (execution only), never span duration, which includes time blocked on user approval — confirmed on live data, one tool measured p95 297s on spans against 8ms average execution in the log. `aggregateToolRepeats` and `findToolEventsForSession` are deliberately NOT split — see their own comments (the former's `(no scope)` drop, the latter documented in `SessionsPage/CLAUDE.md`).
- **A skill invocation is one prompt, not one `api_request`.** Claude Code stamps `skill.name` on *every* model call made while a skill runs, and the attribute propagates into subagents the skill spawns — which carry their own `prompt.id`, so deduplication alone does not exclude them. Counting those rows measures how chatty a skill is, not how often it ran: on the live database that inflated totals 1.7x-46x (`code-review` read 1467 against 11 real invocations) and reordered the ranking, since a skill that fans out to subagents outscored one invoked nearly twice as often. `LogRecordRepository.aggregateSkillInvocationsByModelInRange` therefore drops turns carrying `agentNameAttribute` and takes `DISTINCT ON (identifier, prompt_id)`, attributing each invocation to its **earliest** surviving turn so the per-model split still sums to the row total when one prompt spans models. Do not "fix" this by counting the `Skill` dispatcher's own `tool_result` rows instead — a skill invoked as a slash command never goes through that tool, and that population is ~7x smaller than the truth (10 rows across three months).
- **Configurable event/attribute names.** Dashboard aggregations are driven by `TuningProperties` (`tuning.*` in `application.yml`) — `toolEventName`, `toolAttribute`, `tokenUsageMetric`, etc. Defaults match Claude Code's emission shape. Don't hardcode `"tool_result"` / `"tool_name"` / `"claude_code.token.usage"` in queries or services; read them from `TuningProperties`.
- **Derived cost.** Trace and span cost are computed in SQL from the *reported* per-request figure, not estimated: the `span_costs` / `trace_costs` views (`V14`) sum `cost_usd` across the `api_request` log records Claude Code stamps with a trace id and, when the exporter provided one, a span id. `trace_costs` sums every trace-correlated request log (including ones with no span id) and is authoritative for a trace's total cost; `span_costs` groups the subset that also carries a span id, so it is a per-span **breakdown** of `trace_costs` that can sum to LESS than the trace's total — the two are NOT guaranteed equal, and nothing should filter `trace_costs` down to try to force them to be (that would drop real cost data). Trace-list queries fill `TraceSummary.totalCostUsd` (and the `sort=cost` keyset) with a `LEFT JOIN LATERAL` that re-runs `trace_costs`' predicates against `log_records` per trace rather than joining the view directly — Postgres can't push a window/`LIMIT` past the view's `GROUP BY`, so a plain join re-aggregates every `api_request` log in the table on every page regardless of window size (see `SpanRepository`'s Trace Explorer queries section for the measurements). `TraceService.spansForTrace` fills `Span.costUsd` with one grouped query per trace against `span_costs` (`SpanRepository.findSpanCostsForTrace`) rather than a per-row `@Formula` — the formula ran one correlated subquery per span on every trace-detail load, paid even by callers that never read cost. **The Sessions prompt timeline is trace-correlated** (`LogRecordRepository.findCostSplitByTraceIds` via `LogService.applyTraceCorrelatedActivity`) for any turn that has a trace, so a prompt's cost and the cost on the trace it links to are the same number — but only once per trace: several turns in a row can share one trace, and the trace's cost is billed to the earliest of them only (later turns sharing it are cleared to no cost), so the sum over a session's turns still equals the sum over its distinct traces rather than double-counting a shared one. Turns and traces with no correlated request log fall back to / stay at the counter-derived value (`claude_code.cost.usage`), which is also what per-session totals and KPIs still use. An earlier revision's token-price estimate was removed for running 2-3x off real spend; don't reintroduce a rate table on either side.
- **A turn's own trace-correlated cost is not the same query as `trace_costs`, on purpose.** `findCostSplitByTraceIds` recomputes the identical `SUM(cost_usd)` predicate directly against `log_records` rather than joining the `trace_costs` view, because it also needs a `root_ends` CTE (`spans` filtered to `parent_span_id IS NULL AND name LIKE 'claude_code.interaction%'`, `MAX(end_timestamp)` per trace) to split that total into `own` (billed before the trace's root span closed) and `background` (billed after) — the same total the view gives, plus a second column the view has no way to express. `findToolEventsSplitByTraceIds` mirrors this for tool-call counts. **Fixes a real bug, not a hypothetical one**: a fire-and-forget subagent dispatch (an `Agent` tool call whose own span closes in milliseconds) can keep issuing `api_request`/`tool_result` logs long after the turn that launched it ended — those logs get stamped with whichever `prompt.id` was current when they fired, not the dispatching turn's, so `LogService`'s exact per-request `REQUEST` attribution (joined on `prompt.id`) previously discarded the trace-correlated total entirely and could disagree with the trace detail page by an order of magnitude. Measured on the live database: 4.1% of traces in a 14-day window have request activity after their own root span closes, accounting for 22.6% of all spend in that window — not a rare edge case. `SessionPrompt.costUsd`/`.tools` are now always the turn's trace total (matching what `GET /api/traces/{traceId}/summary` reports for the same trace); `backgroundCostUsd`/`backgroundTools` isolate the post-root-span portion so the dashboard can show *why* a turn cost more than what happened while it was the active turn, not just that it did. **Postgres will not `GROUP BY` a repeated parameterized jsonb expression, even via its own `SELECT`-list alias** — confirmed directly against Postgres (`PREPARE`d, not just via Hibernate): two placeholders bound to the identical runtime string are still different `Param` nodes in the parse tree, so `GROUP BY` validity fails with "column ... must appear in the GROUP BY clause" even for a single occurrence grouped by its own alias. `findToolEventsSplitByTraceIds` works around this by materializing `attributes ->> :toolAttribute` into a plain column via a CTE before the outer `GROUP BY`, which needs no parameter-equivalence proof at all — reach for that shape rather than repeating a parameterized expression in `GROUP BY` anywhere else in this codebase.
- **Per-span effort is a correlation, not an attribute.** Claude Code never emits `effort` on a span -- only on the `api_request` log -- so the `span_efforts` view (`V15`) joins the two on the **`request_id`** attribute and `TraceService.spansForTrace` fills `Span.effort` from it with one grouped query per trace (`SpanRepository.findSpanEffortsForTrace`), the same shape `applySpanCosts` uses. The join key is deliberately NOT `span_id`: as V14 explains, request logs carry the span that was *active* when the request was issued (the interaction root, or a `tool.execution` span), never the `claude_code.llm_request` child that represents the call, so a `span_id` join would attach effort to the wrong span while looking correct. `request_id` is unique on both sides (14,055/14,055 llm_request spans; 14,047/14,047 api_request logs), and input/output token counts agree across all 13,999 joined rows -- the pairing is exact, not a nearest-match. Spans absent from the view keep a **null** effort and the service applies no default, because "not recorded" (~2% of recent calls, more in older data) and "ran at the default level" are different facts.
- **Telemetry collection starts 2026-05-22 — never measure anything over all time.** The first three days are ingest-bootstrap data (19 sessions; counters and `api_request` logs disagreeing by +146% in aggregate; six of the eleven sessions that have EVER diverged more than 2x), and because volume was tiny then and has grown since, that window still skews any query that sums or averages across the whole table. Default every investigative query to a recent window (14-30 days), and **bucket by week to confirm an effect persists before calling it systematic** — a single anomalous week dominating an all-time number is the signature of this trap. This is not hypothetical: an all-time read of exactly this data produced a three-phase plan to fix a "counters undercount by up to 80%" problem that does not exist (measured 2026-08-21, the two pipelines agree within ±4% on every token kind DB-wide, and no session has diverged more than 2x since 2026-07-17). Two related traps from the same episode: distinguish **"the label is absent" from "the traffic is missing"** — the two pipelines use disjoint `query_source` vocabularies (counters emit `main` / `auxiliary` / `subagent`, logs emit `sdk` / `agent:*` / `generate_session_title` / `compact` / `web_*`), so no counter row is ever labeled `sdk` even though it counts the same calls; and before blaming `value_delta` for an inflated counter, check `metric_points.start_timestamp` (OTLP's `start_time_unix_nano`) — a stream's first row legitimately carries its full cumulative value, and that is an overcount only if the series had been running well before the row's timestamp, which it essentially never has (740 of 752 recent `token.usage` streams open within two minutes of their own series start).
- **Two token/cost pipelines that do NOT reconcile.** `metric_points` (cumulative counters, read as `SUM(value_delta)`) and `api_request` log attributes (`input_tokens` / `output_tokens` / `cache_creation_tokens` / `cache_read_tokens` / `cost_usd`, exact per call) both describe spend, and they disagree by tens of percent in **both** directions on real data — dominated by cache-read tokens (one live session: 157.6M cache-read per-request vs 29.3M from the counter; the two pipelines also label `query_source` differently, `sdk` vs `main`). Partial log coverage explains the cases where the request side is lower; nothing yet explains the cases where it is higher. So: pick one source per figure, label which one a number came from, and never add, average, or diff them. The prompt timeline does this explicitly — `SessionPrompt.attribution` is `REQUEST` (summed from the turn's own `api_request` logs, joined on `prompt.id`) or `INTERVAL` (bucketed from counters by timestamp), decided **per turn**, so a session that gained event logging partway through reports each turn however it can be measured. A consequence worth knowing before filing a bug: a session row's `tokenBreakdown` no longer equals the sum of its turns' `tokens`. There is deliberately **no test asserting the two pipelines are approximately equal** — that assertion would fail against real data; `TokenTelemetryQueryIntegrationTest` instead pins the reconciliation that does hold, that a turn's rollup equals its own requests summed.
- **`prompt.id` is the exact turn↔request join key.** Both `user_prompt` and `api_request` logs carry it (verified at 1266/1266 and 13819/13822 rows), which is what lets per-turn rollups be a `GROUP BY` instead of a timestamp-interval bucketing that bills a slow response to whichever turn was open when it landed. `LogRecordRepository.aggregateApiRequestTurnsForSession` / `findApiRequestsForSession` are the query family; `effort` is absent on ~7% of `api_request` rows, so treat it as nullable rather than defaulting it.
- **Derived severity.** Log severity is computed, not taken from OTLP: the `derive_log_severity()` function (`V6`) feeds the stored generated `derived_severity` column (`V8`). The classification defaults are documented on `TuningProperties` and mirrored client-side by `severityOf` in `frontend/src/pages/LogsPage/logsApi.ts` — redefining the function requires a migration that also rebuilds the stored column, so change all three in lockstep.
