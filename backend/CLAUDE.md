# Backend conventions

Project-wide conventions for `backend/` (Spring Boot 4.1, Java 21). Read [../AGENTS.md](../AGENTS.md) for repo-wide context.

## Spring Boot 4 notes

Boot 4 differs from 3.x in ways that bit this project during the upgrade — keep them in mind:

- **Jackson 3** is the default JSON stack (`tools.jackson.*` namespace; `jackson-annotations` stays at `com.fasterxml.jackson.annotation`). Dates serialize as **ISO-8601 strings by default** (`WRITE_DATES_AS_TIMESTAMPS` moved from `SerializationFeature` to `DateTimeFeature` and now defaults to false), so no `spring.jackson.serialization` override is needed for that.
- **Auto-configuration is split into per-technology modules** that are NOT all pulled in transitively. This project explicitly depends on `spring-boot-flyway` (Flyway won't run migrations without it) and the test scope adds `spring-boot-starter-webmvc-test` for the `@WebMvcTest` slice (now in package `org.springframework.boot.webmvc.test.autoconfigure`).
- **Testcontainers 2.x** renamed the Maven artifacts: `org.testcontainers:junit-jupiter` → `testcontainers-junit-jupiter`, `:postgresql` → `testcontainers-postgresql` (Java package names unchanged).
- **`maven-compiler-plugin` is pinned at 3.13.0** on purpose — 3.14+/3.15 regress Lombok+MapStruct multi-round annotation processing and silently drop mapper beans. Don't bump it.

## Module layout

- `ollama/` — the "Analyze trace via local Ollama" HTTP client slice: `OllamaClient` (`@Component`), its `OllamaGenerateRequest`/`OllamaGenerateResponse` wire records (the request's `format` field carries the answer schema when `ollama.structured-output` is on, and is omitted entirely otherwise — see the two-answer-paths note below), and `OllamaUnavailableException` (mapped to a 503 by `ApiExceptionHandler`, message written to be shown directly to the user). `OllamaProperties` (`config/`) is a sibling of `TuningProperties`, not a member of it or of `TuningPropertyCatalog` — that catalog is scoped to OTLP event/attribute-*name* overrides and a reflection test fails the build over anything left unclassified, whereas an Ollama endpoint/model/timeout is a "how do I reach a dependency" setting, the same shape as `spring.datasource.*`. **`OllamaProperties` is the fallback default only** — `base-url`/`model` are each independently overridable at runtime from the Settings page (`ollama_settings`, a singleton row keyed on a fixed id, resolved by `OllamaSettingsService.effectiveSettings()`; a null column means "no override for that field", not "override with null", so a stored row can replace just the model while the base URL still reads the YAML default). Because of this, `OllamaClient` builds NO `RestClient` at startup — `generate(prompt, baseUrl, model)` and `testConnection(baseUrl)` both take the effective values as parameters and build a request client per call from a `baseUrl -> RestClient` factory (created once in the constructor, purely to fix timeouts); baking a single `RestClient` to one `baseUrl` at construction would mean a Settings-page edit needs a restart to take effect. `testConnection` pings `GET /api/tags` (lists installed models, no inference) against a short, separate timeout from the 120s `generate` one, and never throws — a failed connection is a normal outcome for that check, returned as `OllamaConnectionTestResult{success, message}` rather than a 503. **Every generation call streams (`stream: true`), and there is deliberately no buffered variant.** An earlier revision sent `stream: false` purely to avoid parsing Ollama's newline-delimited JSON, which `RestClient.body(Class)` cannot deserialize; the parser is ~15 lines behind `RestClient.exchange` (which is what gives access to the body as a stream rather than an already-buffered array) and buys two things worth more than that. The dialog can show the review being written instead of holding a spinner for the length of a local inference run — see the streaming endpoint below — and the `ollama.read-timeout` budget stops being a deadline for the whole answer: a socket read timeout is measured per read, so streaming it means "120s without a single token" (a genuinely stuck server) where buffered it killed any answer that took longer than 120s to *write*, however healthy the run. A caller wanting the old behaviour passes no listener; a one-chunk non-streamed response is valid NDJSON and needs no second code path. Two details the parser must keep: **`OllamaGenerateResponse.done` is a `Boolean`, not a `boolean`** — the in-band error chunk carries `error` alone and no `done`, and Jackson passes null for an absent record component, so declared primitive the parser died on the very chunk that explains why the run died (caught by a test, not in production) — and **`error` is checked at all**, because Ollama reports a run that dies partway (model unloaded, OOM abort) as a field on an otherwise-200 chunk, so watching only the status code stores a silently truncated review as a finished one. `TraceAnalysisService` (in `service/`) gathers a trace's spans/logs (no new queries — reuses `TraceService`/`LogService`/`TraceExplorerService`), resolves `OllamaSettingsService.effectiveSettings()` fresh on every call (not cached), builds the prompt via `TraceAnalysisPromptBuilder`, and upserts a `trace_analyses` row (`trace_id` as the primary key, so "latest only" is a plain `save()`). **It deliberately carries no class-level `@Transactional(readOnly = true)`**, unlike every sibling service — the Ollama call can take up to `ollama.read-timeout` (120s default) and must run with no transaction open; only the final `save()` is wrapped in a short `@Transactional`. **Staleness detection:** `trace_analyses.last_span_end_timestamp` (`V23`) snapshots `MAX(end_timestamp)` across the trace's spans at generation time (read off `TraceSummary#endTimestamp`, already fetched for the existence check — never null when `traceSummary` resolved, since that Optional is only present when the trace has at least one span). `getStored` re-probes the CURRENT value via `TraceService#latestSpanEndTimestamp` (a dedicated `SELECT MAX(end_timestamp) FROM spans WHERE trace_id = ...` — deliberately not the full `traceSummaryById`/`spansForTrace`, since this fires on every dialog open and shouldn't pay for cost/effort joins or root-span resolution) and sets `TraceAnalysis#outdated` when the trace has picked up newer spans since — the still-running-trace or late-subagent-completion case the frontend flags with a warning banner. A trace whose spans have vanished between the two reads (e.g. a concurrent purge) reads as NOT outdated — "can't tell" defaults to not alarming the user, it does not default to true. `OllamaSettingsService` follows the same rule, for the same reason (`testConnection` calls out over the network). **`regenerate` has a second form taking a `TraceAnalysisProgressListener`**, which is what `POST /api/traces/{traceId}/analysis/stream` runs; the plain `regenerate(traceId)` passes `NO_OP` and delegates to it, so both entry points execute the same code and the streaming one — the one users actually hit — cannot quietly diverge from the tested one. The listener reports a `TraceAnalysisPhase` (`model/`) per occurrence and the model's text as it is written; the phase enum has six constants (`READING_TRACE`, `BUILDING_PROMPT`, `DRAFTING`, `MERGING`, `APPLYING`, `SAVING`) rather than the original four, because a partitioned timeline (see the windowing note below) repeats `DRAFTING` once per review window and joins the results in `MERGING` — everything else before the Ollama call is still milliseconds and would still be invented if listed separately. Each occurrence carries a `PhaseScope` (`stepNumber`/`stepCount`/an optional `detail` string like `"calls 78-140"`) and a `key` distinct per occurrence (`"DRAFTING"` for a single-window trace, `"DRAFTING#1"`/`"DRAFTING#2"`/... for a partitioned one), since a bare phase name can no longer identify which draft a delta belongs to. `TraceAnalysisSseStreamer` sends the real, expanded plan as a `plan` event (`TraceAnalysisProgressListener#planned`, called from `TraceAnalysisService#regenerate` once `preparePrompt` has decided the window count) once that count is known, after the `started` event's optimistic one-entry-per-phase list. The answer-character counter reported alongside each delta is now owned by `generateAndSave` and threaded through every `generate()` call in the run (every window plus the apply-this call) rather than allocated fresh per call, so it only ever increases for the run's lifetime. `label` still travels to the client with the id, so renaming or adding a phase needs no frontend change. **`OllamaGenerateRequest` always sends an explicit `options.num_ctx`** (`ollama.context-tokens`, 24576): Ollama applies its own default context window (4096 tokens on current releases, 2048 on older) when the field is absent and then **silently left-truncates** a longer prompt — no error, no response field saying so — which for this prompt means chopping off the instructions and trace overview at the top while keeping the raw trace tail. `ollama.max-prompt-chars` (60000: ~10.5k of fixed review instructions plus enough room for a large trace whole, or for one review window when it doesn't fit whole) is only an enforceable budget because `num_ctx` is sized to hold it; changing either without the other reintroduces silent truncation.

**The answer can be produced two ways, and which one is better is a measurement, not an opinion.** `ollama.structured-output` (default **off**) swaps the prompt's answer contract for a JSON Schema sent as Ollama's `format`, deserializes the reply into `TraceAnalysisAnswer`, and renders the stored markdown from it in code. What that buys is that the answer's *shape* stops being something a 7B model can get wrong: it cannot write its review twice (the only reason `collapseDuplicatedBlock` exists), cannot drop or misspell an "Apply this" line, and **cannot name a rule target off the closed list** — `putSkills`' evidence-built targets become a schema `enum` rather than a sentence asking the model to copy one of N strings verbatim, which is exactly the instruction that lost on trace `5d6c9ca05d7c6ce12e41a84980693f10` even after the list was reordered to put the skill first. What it may cost is answer *content*, since every token is then drawn from a grammar-restricted distribution — an effect that depends on the operator's model, which is why both paths stay runnable and the default is off until `TraceAnalysisRegressionHarness` says otherwise on that machine. Three things are deliberate. The **caps are enforced in `toMarkdown`, not as schema `maxItems`**: array-length keyword support varies across Ollama's schema-to-grammar conversion, and an unsupported keyword silently changing behaviour on someone's machine is not worth it — the two/five caps are this application's editorial call anyway, like the observation gating. **Every field is `required`, with `None` a member of the target enum**, so the model always has a legal token and never has to choose between inventing advice and emitting an incomplete document — the same trade the prose contract makes with "either text the reader can paste, or the single word None". And a **parse failure is raised, never repaired**: the likeliest cause is an Ollama old enough to ignore an unknown `format` (the same silent-ignore shape `num_ctx` documents), and storing the prose it returned instead would hide that misconfiguration behind an answer that looks fine. **A fourth constraint was added after the fact, and its absence is instructive: `wentWell` is omitted from the findings schema outright when `buildObservations` verified no positive.** Every gate above was written into the schema because prose had already lost; the positives section was left gated by prose alone (`hasPositiveObservations` switches the template's section and its "write exactly the two/three sections" count), and on the structured path that gating did nothing at all — the schema handed the model a legal `wentWell` array on every trace regardless of what the template said. Trace `adae1753270dd3088520435ae7f8af94` is the bill: a trace with no verified positive (first tool call a `Bash` grep naming no file, no subagent dispatched — the only two shapes that qualify) opened its review with *"Cost Distribution — the main loop carried the cost with a high effort model call that was well justified by the complexity of the task"*, praise nothing supports, on a trace where **all 26 model calls ran at `effort=high`** so no call was distinguishable that way; it reads as the cost-driver observation (call 1 took 28.6% of spend) inverted into a compliment. The field is **omitted rather than capped with `maxItems: 0`**, for the same reason the two/five caps are not schema keywords, and the parse side already handled it — Jackson passes null for an absent field and `capped` maps null to an empty list, so `findingSections` drops the section exactly as it does for an empty array. `TraceAnalysisAnswerScorer.answerShapeViolations` checks the same thing from the other side (an answer carrying a `**What went well**` heading against a prompt carrying no `Went well:` line) and stays even though the schema now makes it unreachable, because it is the **only** thing covering the prose path — where that section is still gated by template prose alone. Stored rows are markdown either way, byte-identical in shape, so the flag flips without migrating `trace_analyses` and the frontend needs no change. `TraceAnalysisService.preparePrompt` is a separate step from the model call for the harness's sake — see below.

**`TraceAnalysisRegressionHarness` scores the review against traces whose right answer is already known.** A developer tool, not a CI test: it needs a live Ollama and the operator's own database, so it is gated on `TRACE_ANALYSIS_HARNESS=true` (`-Dtest=TraceAnalysisRegressionHarness`; `TRACE_ANALYSIS_HARNESS_TRACES` scores an ad-hoc comma-separated list instead of the corpus, with shape checks only). It exists because every change to this feature so far — the slash-command fence, the preceding-turn section, the `answersPrecedingQuestion` verdict, the outlier gating — was judged by regenerating one trace and reading the answer, which says nothing about the failures fixed last month. The corpus is those failures with the sentence each must no longer produce: `5d6c9ca0…` (must not judge `/ship`'s wording or review the previous trace's work), `83b37f35…` (must not call "yes fix it" vague), `1635329e…` (must not fire the fresh-session rule on a continuation). **The highest-signal check is mechanical**: every `call N` the answer cites must exist in the timeline *and* be the kind of call the answer says it is — the documented failure mode, llama3.1 reporting "calls 21 and 26 are identical TodoWrite" when both are model calls. Its oracle is **the rendered prompt**, not a renumbering of the spans, which is why `preparePrompt` is package-visible as its own step: a second implementation of the call numbering would be free to drift from the one the model was shown and then accuse a correct answer. The kind check fires only when the clause after a citation names exactly one call kind (and stops at the sentence end, an actual bug these tests caught) — ambiguity is unscored, because a checker that cries wolf gets switched off. **The scoring lives in `TraceAnalysisAnswerScorer`, separate from the harness and covered by `TraceAnalysisAnswerScorerTest` on every build**, precisely because the harness itself never runs in CI. It scores only what an answer must *not* say; whether the finding it made was worth making is not automatable, so the harness always prints the answers and the assertions are a floor, not a verdict. Runs vary, so treat one violation as a re-run and a repeated one as a regression. Two checks were added after the fixes above, and one of them breaks this class's own rule on purpose. `duplicatedWordingViolations` is ordinary — it catches the `Better wording:`/`Fix:` repeat from the prose path and acts as the regression net under the rendering fix. `unreportedFailureViolations` is the exception: it is a **coverage** check, the opposite shape of "score only what an answer must not say", and it exists because the answer contract makes failure recovery a *named obligation* ("for each FAILED or REJECTED call ...") rather than one candidate finding among many — on `adae1753270dd3088520435ae7f8af94` the trace's only failure went unmentioned across three runs while the review found room for three other bullets. It is kept as narrow as that justification: it fires only when the prompt's observations report a failed **tool** call, and any mention of failing at all satisfies it. It does not ask that the mention be a finding, be correct, or cite the right call — that would be judging the finding's worth, which is the line the rest of this class does not cross. Don't widen it into one.

**The citation-matching regex was itself blind on a large share of real answers, until it was widened to match a whole citation phrase rather than a bare `call N`.** `CITATION` used to be `\bcalls?\s+(\d+)` — "call"/"calls" immediately followed by whitespace and one digit run — which cannot match `call number 6`, `call numbers 57, 119, 136`, `calls 15 and 16`, or `calls 3, 4 and 7`, every one of which is real, observed phrasing: trace `df8c757de3bfbfe9c1da2b29f431a192`'s stored answer contains `"at call number 6"` and `"(call numbers 57, 119, 136, 59, 148)"`, neither of which the old pattern could match at all, so `citationViolations`' kind-check silently never ran on either. This is the identical bug already hit and fixed on the frontend for the identical reason — `callCitations.ts`'s own note on trace `bc222c551f5acf3c77fc44f8bc53c0f8`, where every citation read `(call numbers 27, 29, 31)` and none of them linked. `CITATION_PHRASE` is now a close port of that file's `CALL_CITATION_PHRASE` (`\bcalls?\s+(?:numbers?\s+)?#?\d+(?:\s*(?:,|and|&|through|to|–|-)\s*#?\d+)*`, case-insensitive), matched first as a whole phrase and then walked with a second, simpler `CALL_NUMBER` (`\d+`) matcher to pull every individual call number out of it — mirroring the frontend's two-stage phrase-then-numbers split exactly, so the two stay in step if either widens further. Every number sharing one phrase is checked against the same clause (`claimedKind`, unchanged), since a group's whole clause — from the phrase match to `CALL_KIND_WINDOW_CHARS` past its end — describes every number in it equally, not just the first.

**One check now runs on the generation path, and it is deliberately not the scorer.** `TraceAnalysisAnswerScorer` lives in test scope and is only invoked by the harness; the obvious move — promote it and run it live — was measured first and does not work. Run against trace `9ab1feeebdd15a449bbc4c9983dcb79d`'s stored answer with that trace's own 21-call timeline, `citationViolations`, `fileCitationViolations` and the aggregate `score` **all return empty** on a review whose opening bullet reads *"Calls 2 and 5 are identical, and 6 is a repeat of 12"* — call 2 is a Bash grep and call 5 is a model call. `claimedKind` cannot fire because it only reads a claim about what *kind* a call is, and "are identical" names no kind; it correctly declined to score a sentence it had no rule for. The missing rule is a **sameness claim** — a relation asserted between two calls rather than a property of one.

**Checking kinds was not enough, and the trace said so on the very next run.** The first version of `TimelineCitations` faulted a sameness claim only when the cited calls were different *kinds*, which is provable without judging what they did. It fixed that sentence, and the next regeneration of the same trace produced *"Calls 7, 9, 11, 13, 15, 17, 19 were unnecessary and repeated the same work"* — seven `llm_request` calls, so one kind, so a kind check has nothing to say. They are the ordinary agent loop between tool calls, with outputs from 97 to 918 tokens; nothing repeats. So `unsupportedSamenessViolations` validates against **what the prompt actually says relates two calls**, which is the same oracle `fileCitationViolations` already uses. There are exactly four such signals and `samenessIn` reads all of them: the folded adjacent range in a line's own `12-14.` prefix, the `[identical call repeats at N, M]` forward marker, the `(repeat of call N)` back-reference, and the `[same file, different input, at N, M]` revisit marker. **The revisit marker counts as support even though it means the inputs differed** — a review calling that "repeated work on one file" is describing exactly what the marker records, and faulting it would punish a correct finding. What is caught is an identity claim the prompt supports in *no* way at all. **Absence of a marker is usable evidence only because the markers survive every `TimelineDetail` level**: that enum varies the tool-input length, the success outcome and the model-call breakdown, while the grouping that produces these markers runs unconditionally, and a tighter level can only produce *more* links (shorter inputs collapse into one group), never fewer. Five conservatisms, each a class of false positive: 2+ calls in one citation phrase; an explicit sameness word (`identical`/`the same`/`duplicate`/`repeat` — "similar" and "related" are excluded, they claim no identity); only calls the timeline contains (an unknown number is `citationViolations`' finding, and faulting one sentence twice helps nobody); nothing on a line whose marker was abbreviated to `and N more`, whose real links cannot be read; and **every** cited pair must hold, since letting one genuine repeat inside a list of seven excuse the other twenty pairs is how a checker stops catching what it was written for. **The offending fault is dropped, not annotated, and the drop is logged at INFO**, in `TraceAnalysisService.dropUnsupportedSamenessFaults` — a stored review reads identically whether the model wrote one fault or wrote two and had one removed, so without the log there is no way to tell how often the check fires, or to notice it firing on a finding it should not have. It runs before the findings are rendered — so it reaches neither the stored review nor the second model call, which on the first of those runs is where the `Instruction rule` had been hung on it. Dropping every fault is legal: `hasFaults` then skips the second call and the review degrades to the empty-review sentence, while the settled `Tool swap` survives regardless, being evidence this application verified rather than anything the model wrote. **`TimelineCitations` owns the timeline/citation regexes and the clause window now, and the scorer aliases them** rather than keeping a second copy — the `CITATION_PHRASE` widening already had to be applied twice (here and the frontend's `callCitations.ts`), and a third copy is a third place to miss it. Structured path only, like the settled tool swap. What this does **not** cover: the same trace's *"the final response does not deliver the answer"* bullet, which is false (the single `assistant_response` opens "Yes — there's meaningful headroom") but is a semantic judgment about prose, not a checkable claim about a call. **Even fully fixed, the widened citation check only verifies a call's *kind*, and that is not the class of error that slipped through uncaught on real data.** The stored answer for trace `df8c757de3bfbfe9c1da2b29f431a192` opens with *"The file `AnalyzeTraceDialogView.tsx` was read multiple times (call numbers 57, 119, 136, 59, 148)"* — every one of those five calls is genuinely a `Read`, so the kind check has nothing to flag, but 2 of the 5 (59, 148) actually touched a **different** file, `AnalyzeTraceDialog.tsx` (no "View"). `fileCitationViolations` is the companion check this gap needed, built on a `timelineCallTargets(prompt)` sibling to `timelineCallKinds` — same oracle, the rendered prompt, never rebuilt from spans, for the identical reason `timelineCallKinds` already gives. It works because `TraceAnalysisPromptBuilder#toolInputFor` renders a Read/Edit/Write call's tool_input as the tool_result log's own JSON string directly into the timeline line (confirmed against real `log_records.attributes->>'tool_input'` data: `{"file_path":"/Users/.../frontend/CLAUDE.md"}`), so a plain `"file_path"\s*:\s*"([^"]*)"` search over each numbered line finds it — and, because that JSON string is truncated to the current `TimelineDetail`'s `toolInputLength` cap, a value cut off before its closing quote simply fails to match rather than yielding a mangled path, the identical "skip rather than guess" conservatism `claimedKind` already applies to an ambiguous clause. **The check reads the whole sentence around a citation, not just the clause after it** (`sentenceAround`, expanding to the nearest sentence/line boundary in both directions, mirroring `clauseAfter`'s logic bidirectionally) — because a real finding states the file name *before* the call-number list, as the example above shows, so a forward-only window would miss it entirely. Within that sentence it requires **exactly one** backtick-quoted, file-extension-shaped token (`` `([\w.\-]+\.[A-Za-z0-9]{1,10})` `` — this feature's own markdown convention for naming a file, per `AnalyzeTraceDialogView`'s inline-code-chip styling) and a **known** target for the cited call; zero, several, or an unresolved target are all left unscored rather than guessed at, the same conservatism the kind check applies to ambiguity. `TraceAnalysisAnswerScorerTest` proves this against a synthesized minimal prompt reproducing the trace's actual shape (two Read calls touching `AnalyzeTraceDialogView.tsx` and `AnalyzeTraceDialog.tsx`), with a positive case (the mismatch is caught), a negative case (a citation naming the right file is not flagged), and a target-unknown case (a Bash call with no `file_path` is not flagged either).

**The kind and file checks now run live too, promoted rather than copied — and getting them onto the generation path surfaced two bugs the harness-only path never could, because it only ever regenerates real traces, never a hand-built two-call fixture.** `citationViolations`/`fileCitationViolations`' bodies moved into `TimelineCitations` as `miscitedKindViolations`/`miscitedFileViolations` (the scorer's two methods are now one-line delegates, kept for their existing signatures and the exact violation strings `TraceAnalysisAnswerScorerTest` asserts on); `TraceAnalysisService.dropMiscitedCallFaults` runs them per window, right after `dropUnsupportedSamenessFaults`, same drop-not-annotate doctrine, same INFO log. Motivated by trace `299f2704e7161e2271a5c3749cdf3551`, whose stored review claimed *"Used `grep -n` for file searches at calls 22 and 155, which could be more efficiently handled by the dedicated `Read` tool"* — call 22 is a model call, not the `Read` the sentence's own follow-up clause names it as. **First bug: `renderLlmRequestLine` always renders a model call as `"- llm_request ..."`, a literal hyphen ahead of the real token** (confirmed against `TraceAnalysisPromptBuilderTest`'s own `contains("1. - llm_request")` assertion), so `TIMELINE_LINE`'s `(\S+)` capture read every model call's "kind" as a bare `-`, not `llm_request` — and that dash then spuriously matched any hyphenated word elsewhere in a citing sentence ("re-reading", "well-tested"), making `claimedKind` see two candidate kinds in the clause and decline to score on ambiguity, silently. `unsupportedSamenessViolations` was never affected: it only checks `containsKey` and the separately-built marker adjacency, never the kind *value*, so this went uncaught until a check that compares kind equality existed. Fixed by widening `TIMELINE_LINE` with an optional `(?:-\s+)?` skip ahead of the capture, the same shape the existing `(?:\[[^\]]*\]\s*)?` subagent-prefix skip already uses. **Second, larger bug: `callKindsIn`/`callTargetsIn`/`samenessIn` scanned the WHOLE rendered prompt, not just its timeline section** — and `trace-analysis-prompt.mustache`'s own answer-writing rules render as a numbered list too, `"1. **Prefer the verified observations.**"`, `"2. **Never invent prompt or response wording.**"`, well after the real timeline. `TIMELINE_LINE` cannot tell the two apart (both are `^\d+\.\s+\S+`), and the later match wins `Map#put`'s overwrite, so a real two-call trace's `callKinds` came back `{1: "**Prefer", 2: "**Never"}` — the genuine entries clobbered before any check ran. This is invisible to `unsupportedSamenessViolations` for the identical reason the dash bug was: it never reads the value. It is why every existing `TimelineCitationsTest` fixture — none of which include the answer-writing rules — never caught it, and it only surfaced building a NEW test against a real regenerated prompt rather than a hand-written snippet. Fixed with `timelineSectionOf(prompt)`: find `"## Call timeline"` (the heading `trace-analysis-prompt.mustache` always renders immediately before the numbered lines, windowed or not), find the next level-2 `"\n## "` heading after it (whichever section the template renders next — Verified observations, Errors, or straight to What to look for when the trace has neither), and scan only that slice. Falls back to the whole input when the heading is absent, which is every hand-written test fixture in this class and the scorer's, so no existing test needed touching. **Neither bug reached the reader before now** — the sameness check's own conservatism (needs an explicit sameness word AND two-or-more calls AND no unreadable marker) meant a corrupted kind value never actually flipped one of its outcomes on real traces, which is exactly why two structural bugs sat undetected in code that had been live and tested for weeks. `CALL_KIND_WINDOW_CHARS` was separately widened 60 → 100 for the same motivating sentence: `Read` sits 71 characters past the citation in that trace's real, unbroken sentence (no earlier `". "` or newline to stop at), past the original cap. The sentence/newline stop is what actually guards against spilling into a different sentence about a different call; the character cap is only a backstop against one unbroken sentence running unreasonably long, so widening it to fit one real, ordinary-length sentence carries the same risk profile 60 did — confirmed by re-running every existing `TimelineCitationsTest` case unchanged. **Known, accepted gap, not addressed by any of the above**: the same stored review also mis-cited a redundant-read finding at *"calls 93 and 101, suggesting inefficiency in file handling"* (93 is a Bash grep; the real duplicate Read pair is 95/101) — this sentence evades every check, because its sameness word ("the same file") sits *before* the citation rather than in `clauseAfter`'s forward-only window, and it names no call kind or backtick-quoted file next to the citation either. Widening the sameness check to read bidirectionally, the way `miscitedFileViolations`'s own `sentenceAround` already does, would close this; left as a follow-up. `TraceAnalysisRegressionHarness`'s corpus pins only the fabrication that is actually fixed (`"at calls 22 and 155"`), not the one that is not — a forbidden phrase the code cannot prevent would fail the harness on an unrelated, pre-existing gap rather than a real regression.

**What the trace-analysis prompt actually contains, and why it reads logs rather than spans for tool inputs.** `TraceAnalysisPromptBuilder` does NOT dump every span and log — it projects them into an overview (the same headline figures the trace detail page's SummaryStrip shows: cost incl. the background split, duration, span/tool/model counts, max depth, errors, four-way token breakdown, time attribution), the full user prompt, a condensed call timeline, errors, and the full final assistant response. The timeline's tool inputs come from **`tool_result` logs, never the tool span**: measured on this database, `tool_input` is present on **0 of 9,225** `claude_code.tool` spans (they carry `file_path` at 44% and `full_command` at 48% instead), while the `tool_result` log carries the full `tool_input` JSON at 100% along with `success`, `duration_ms` and `error`. An earlier revision read it off the span, so every tool line rendered as a bare name with an empty target and the prompt's central "compare what was searched for against what the prompt asked for" instruction had no data behind it. Spans stay the ordering backbone and each tool span is enriched from its `tool_result` log by the exact `tool_use_id` both signals carry (the same correlate-on-the-exact-key approach `LogService#resolveLeafSpans` takes), falling back to the span's own `file_path` when logs are absent — **with one exception: a shell command is read off the span's `full_command` ahead of the log.** Claude Code truncates long values inside `tool_input` *before export*, leaving a `…[N chars]` marker where the body was — measured over 30 days that hits **531 of 6,826 Bash rows (7.8%)**, and 2,295 of 13,843 `tool_result` rows overall across seven tools — while the span's `full_command` is never truncated (**0 of 6,847** Bash spans carry the marker, at up to 12,135 characters). For commands the log is therefore a lossy copy of something the span already holds intact, the same reasoning revisit detection uses to take `file_path` off the span. Commands are then truncated **middle-out** rather than head-first (`truncateMiddleOut`, tail-weighted 60/40 within the same 200-character cap), because a chained command reads `setup && action && verify` and head truncation drops the verify — a one-directional failure that cannot hide a missing check, only invent one. Both halves are load-bearing and neither works alone: on trace `5d6c9ca05d7c6ce12e41a84980693f10` the review reported the agent shipped *"without explicitly confirming the success or failure status of the critical preceding tool calls"* and wrote a standing rule demanding a verification step, while that call's own command ended `&& git push -u origin … && git status` at character 1,352 of 1,352; preferring the span alone would still have lost the tail to head truncation, and middle-out over the log's copy would only have centred on `…[1352 chars]`. The trade this accepts is the agent's own `description` field, which lives only in the log's JSON — the command is the evidence, the description is the self-report the review should be judging against rather than accepting. Note **36% of all Bash commands (2,462 of 6,847) exceed the 200-character cap**, so this path is normal, not an edge case, and it fires regardless of budget headroom: the 200-character `TimelineDetail.FULL` cap applies whether or not `partitionToBudget` ever has to window the trace, so a 10-span trace using well under its budget still truncates every command at 200. `llm_request` spans carry `model`/`input_tokens`/`output_tokens`/`cache_read_tokens`/`stop_reason`/`attempt` directly at 100%, so per-call model detail needs no join back to `api_request` logs — **except cost**, which is the one figure the span cannot answer (see the cost/subagent paragraph below). Rejected `tool_decision` rows are rendered onto the rejected call's own timeline line rather than as a separate section. **Every duration the prompt renders goes through `formatDuration`** — the overview, the time attribution, each timeline line and the outlier observation — because the review quotes back the shape it was shown: a prompt reading `Duration: 36411 ms` produced findings reading "36411 ms", leaving the reader to divide in their head to learn the call took half a minute. The ladder is whole milliseconds below a second (`812ms` — the resolution the underlying attribute has, and where a tool call normally sits), then `36.4s` / `2m 5s` / `1h 12m`, extra digits above a second being false precision in a sentence. Asking the model to convert instead would be arithmetic handed to a 7B model in prose — the same trade `buildObservations` exists to refuse. **Timeline calls are numbered** (so the model can cite "call 12", and so an elided middle shows exactly where and how much is missing), **non-adjacent repeats fold to back-references** (the first occurrence names where it recurs, later ones shrink to `40. Read (repeat of call 3)`), and **an overflowing budget is paid for in per-call detail, not in calls**. `TimelineDetail` re-renders the whole timeline at successively tighter levels — the tool-input cap drops 200 → 80 → 30, the `-> ok` and duration come off calls that succeeded, and a model call's token/cost/effort breakdown comes off — and the first level that fits is sent, so every call keeps its line and its number. What each level gives up is chosen so **nothing a finding rests on is ever dropped**: a failure, its error body, a rejection, a blocked-on-user wait, an oversized result and a subagent dispatch summary render identically at all three. Losing calls is the one compaction the review cannot recover from, because `buildObservations` and the answer's citation contract are both written against call numbers — an elided call is a number the model is invited to cite and cannot see, over exactly the stretch of work the redundancy and error-recovery questions are asked about. Trace `8f98bde5c347e9844362370f41f1c5ac` is why this is not theoretical: 95 timeline calls (63 of them inside one `general-purpose` dispatch, each carrying a `[general-purpose] ` prefix) overflowed at 33k, and on the version of this feature that elided a middle stretch, the review that came back cited "calls 31 through 95" as one opaque block it could not read. **Elision no longer exists at all.** Since `partitionToBudget`, a timeline that overflows even at `MINIMAL` detail is instead split into consecutive, non-overlapping review WINDOWS — each a complete, independent model call with its own header and carry-over block (files touched, failures seen, spend so far, computed once per `build()` and sliced per window) — and the per-window findings are joined in code by `TraceAnalysisFindingsMerge` before the unchanged single apply-this call runs against the merged result. No call is ever uncitable: `packWindows` only thins per-call detail or, for one oversized line, hard-truncates its middle (`fitLine`) — it never drops a call. The detail level is chosen once, globally, never per window, because the exact-repeat and revisit markers are facts about the WHOLE call list and a per-window level could render the same call two contradictory ways. **Which level wins is the operator's call, because the two remedies trade against each other and the right trade depends on the model.** `ollama.timeline-detail-preference` decides it: `FEWEST_REVIEW_WINDOWS` (the default) tries every level loosest-first and takes whichever needs the fewest windows, ties favouring the loosest, so a trace pays in per-call detail before it pays in model calls; `MOST_TIMELINE_DETAIL` inverts that, holding the timeline at `FULL` and partitioning as far as the budget requires. The default is the cheaper one, not the better one — at `max-prompt-chars` 60000 no measured trace partitions at all, so a small model gets one ~24k-token prompt on every trace, and thinning detail is what the ladder's own contract warns is only safe for calls where nothing went wrong. Each extra window is a full model call re-paying the fixed ~10.5k of review instructions, which is the cost side. Which wins on a given model is a measurement, and `TraceAnalysisRegressionHarness` settles it exactly as it settles `ollama.structured-output`. Measured caveat on the repeat folding: only **3.9% of tool calls** (517 of 13,408 over 30 days) are exact `(tool, tool_input)` duplicates, so it saves ~2.9% of timeline characters and moves no trace below the budget — its value is making redundancy *visible*, not compaction.

**Sections B and C are asked once per trace, not once per window.** Every window used to re-render the full "Request quality" and "Cost, time and context" sections, over evidence — the request's own wording, the trace's cost split — that does not change between one window and the next: a partitioned trace gave every window an equal, independent chance to fabricate a wording fault or a cost verdict, and `TraceAnalysisFindingsMerge` orders survivors round-robin across windows specifically to cover the trace evenly, which multiplies rather than dampens a fabrication that shows up in more than one window's answer. `judgesRequest`/`judgesCost` context flags now gate each section to exactly one window — the first for B (the earliest calls are where a target-finding search would show up, and `TraceAnalysisFindingsMerge#mergedRequestKind` already breaks a request-kind tie towards the first window's vote) and the last for C (its carry-over block already summarises spend and files touched across every prior window, which is better evidence than window one has). Every other window renders a one-line "judged in another pass. Skip it." placeholder instead of the section body, so the heading a reader might grep for is still there. On the structured-output path the gating reaches the schema too: `TraceAnalysisAnswer#findingsJsonSchema` takes a second boolean and omits `requestKind` from a non-judging window's grammar entirely, the identical "absent, not empty" treatment `positivesAllowed` already gives `wentWell` — a verdict the window is not asked for is not a token the grammar can produce, not merely one the prompt discourages. A single-window trace has both flags default `true` and renders byte-identical to before this existed; `frameLength`'s own budget probe leaves them `true` too, so the per-window character budget stays sized for the widest section content a window could ever carry.

**Token counts in the Overview are rendered in the same units as the benchmark text they are compared against**, through a `formatTokens` sibling to `formatDuration`: below 1,000 the exact count, then `12k`, then `1.5M`. The line reading "typical traces here start around 100k and three quarters of them never exceed 170k" used to sit directly above a bare seven-digit integer for the trace's own starting context, asking the reader — or the reviewing model, in prose — to do the rounding themselves before the comparison meant anything. Scoped to the Overview's token fields only (input/output/cache-read/cache-creation, the cache-mix intro, and the context-size starting/peak figures); the "Verified observations" text `contextSizeObservations` writes for the large-starting-context and steep-growth findings builds its own strings independently and is unaffected, since a finding's own detail sentence is not being read against the benchmark line the way the Overview figure is.

**Revisit detection covers the shape exact matching misses**, and is the bigger of the two: a `[same file, different input, at 40, 90]` marker on the first call whenever the same tool touches the same file again with a different input (a re-read at another offset, a re-search with another pattern). Measured over the same window this flags **2,353** repeat calls against exact matching's 517, and puts a marker on **238 of the 432 traces** that touch files at all (55%, against 15% for exact repeats). Three deliberate constraints: it keys on `(tool, file_path)` so Read-then-Edit on one file — how an edit normally happens — is not flagged; it **annotates only**, never collapsing the later line, because a second offset is genuinely not the first one; and a group already named by the exact-repeat marker is excluded so one line never carries two markers for the same fact. The file comes from the **tool span's own `file_path` attribute**, not from parsing the `tool_input` JSON: measured over 13,488 calls the two agree on 5,842 and the span carries it slightly more often (5,858 vs 5,847), and the span attribute cannot be cut off mid-path by the 200-character `tool_input` truncation. **`api_request_body` / `api_response_body` are deliberately never read, and no summarization pass exists.** The question "summarize the bodies in batches to fit them in" was measured rather than guessed, and the answer is that the bodies contain nothing the prompt does not already get for free. Over 14 days a trace's **request** bodies total **2.0M characters at p50 and 39.4M at p95** — every request re-sends the whole conversation — so a map-reduce with a local 7B model (measured throughput: ~14.6k prompt characters in ~9s) would run for tens of minutes to hours per trace against a 120s read timeout. **Response** bodies are far smaller but are **35% base64 `signature` blobs**, carry `thinking` already `<REDACTED>`, and the assistant prose inside them is **7.6% of their bytes**; extracting that prose gives p50 1,146 / p95 12,648 characters per trace, which matches what the plain `assistant_response` logs already carry (p50 1,135 / p95 12,483) to within 1% — in a clean attribute, with no JSON parsing, no base64, and no `\u0000` escapes (which break a `::jsonb` cast on this data outright). So `buildAssistantTurnLines` reads those logs and includes **every** assistant turn rather than only the last, capped per turn (1.5k for intermediate turns, 4k for the final one that ask-vs-delivered is judged against) and middle-out trimmed at a 12k section budget — sized so a p95 trace's narration (12.5k characters) survives essentially whole rather than being clipped to status fragments. If richer conversation content is ever wanted, extend from the `assistant_response` logs; do not reach for the bodies, and do not add an LLM pre-pass.

**A cited call number reaches the trace detail page as `Span.callNumber`, and the rule behind it lives in exactly one place.** The review cites its evidence by call number ("Call 20 was an outlier") and nothing on the page carried that number: the waterfall's index badge counts **every** span in DFS order — the `claude_code.interaction` root, each tool call's `tool.execution` and `blocked_on_user` children — while a call number counts only `toolSpanName` and `llmRequestSpanName` spans in trace order. On a real trace (`e93c8af230c706c9bf29d6df2738f4eb`) the two diverge from the first row, so a reader had no way to walk from a citation to the call it is about, which is the one thing every finding rests on. `TraceCallNumbering` now owns both halves of the rule — `isCall`, which `TraceAnalysisPromptBuilder` delegates to, and `callNumbersBySpanId`, which `TraceService.spansForTrace` fills the DTO field from over the same `start_timestamp`-ordered list the builder is handed. Numbering is **positional over the whole list**: a span carrying no span id still consumes its number (dropping it would renumber every call after it and silently invalidate the model's citations) and simply gets no map entry. A second implementation of the numbering is the thing to avoid here — it would be free to drift, and a citation pointing at the *wrong* row is worse than one pointing nowhere; `TraceAnalysisPromptBuilderTest.callNumbersInTheTimelineMatchTheOnesPutOnTheSpans` pins the two against the **rendered** timeline rather than against each other's code, the same oracle choice `TraceAnalysisRegressionHarness` makes.

**Per-call cost, and which sub-agent spent it, are resolved in one pass over the spans (`attributeCalls`).** Two facts make this possible without a new query, and one trap makes it necessary. The trap: `Span#costUsd` comes from the `span_costs` view, which groups request logs by the span that was merely *open* when the call was issued — measured over 7 days, every dollar in that view sits on a `claude_code.interaction` ($193.83) or `claude_code.tool.execution` ($86.38) span, and **not one lands on the `llm_request` span that made the call**, so reading cost off the model call's own span yields zero. Money is therefore attributed the way `span_efforts` (V15) attributes effort, on the `request_id` both signals carry (14,047/14,055 rows pair exactly). The first fact: **a sub-agent's work lives in the dispatching trace**, as `llm_request`/`claude_code.tool` spans whose ancestor chain runs through the `tool.execution` child of the `claude_code.tool` span with `tool_name=Agent` — confirmed on a real trace where that one execution span had 94 children. The second: its `api_request` logs carry `query_source` = `agent:builtin:<type>` / `agent:custom`. Both are read, for different jobs: **ancestry says which dispatch** (so cost lands on a call number the reader can find, and so three project-local agents in one trace do not collapse into one bucket — Claude Code names every one of them `custom`), **`query_source` says which agent**, and anything neither main-loop (`mainLoopQuerySources`) nor subagent-prefixed is bucketed as auxiliary so session-title generation and compaction never read as the agent's own spend. The result is a "where the model spend went" block in the overview, a `[Explore]` prefix on each sub-agent line, a `[ran Explore: N model calls, M tool calls, $X]` summary on the dispatching Agent call itself, and a gated observation naming a sub-agent that took ≥40% of the trace's measured spend. This is not a marginal case: over 7 days, $86 of $280 of span-attributed cost sat inside sub-agent runs.

**Cache reuse and context size are reported against this database's own distribution, and gated on it.** Both answer questions the SummaryStrip cannot: was the prompt cache actually reused, and did this request belong in this session at all. The cache figure is cache reads as a share of *prompt* tokens (input + cache read + cache creation) — output tokens are deliberately out of the denominator, since folding in what the model wrote makes a chatty trace look cache-efficient. Measured over 30 days and 891 traces, per-trace cache-read share is **p50 96.8%, p25 86.2%, p10 0%** (the bottom decile being single-call traces with nothing to reuse yet), so the observation fires only below **70%** and only with ≥3 model calls; the overview line quotes the 96.8% median so the model has something to judge against rather than a bare percentage. Context size is measured on **main-loop calls only** — a sub-agent runs in its own small fresh context and mixing those in drags the figure towards nothing, which is the opposite of the answer, since a large main-loop context is exactly what makes dispatching a sub-agent right. Against the same window a trace's first main-loop call carries **p50 104k / p90 355k** prompt tokens and its largest **p50 96k / p75 168k / p90 280k**, so "began on an already-loaded context" fires at **200k** on the first call (with a pre-written rule about starting unrelated work in a fresh session — the fix genuinely is a new session, not better wording) and "grew steeply" fires at a **300k** peak that is also ≥2x the start. Growth alone is not gated on the multiple: 5k growing to 20k is 4x and fine.

**A follow-up request is not vague, and judging it in isolation was the review's most common false finding.** "yes implement those two" reads as under-specified wording until you see that the message it answers ends *"Want me to implement those two?"* — a real pair from this database. `LogService#lastAssistantResponseBeforeTrace` fetches the newest `assistant_response` log in the same session strictly before the trace's `startTimestamp` (excluding the trace's own logs), and the prompt renders its **tail** — what a reply answers is the question the previous message closed with, not its opening paragraphs — with the gap ("4 minutes before this request was sent"), plus an instruction in section B to resolve the request against it before calling anything ambiguous. Deliberately not restricted to the immediately preceding *trace*: a turn can emit several assistant messages and the newest one is the one being answered, whichever trace emitted it. **The section renders only when `hasPrompt` — never for a slash command, a `<task-notification>` envelope, or a trace with no `user_prompt`.** Those three drop section B, so there is no wording left for the preceding turn to resolve, but it stays the one block of free prose in the prompt; and on a clean trace the verified-observations block is empty while the answer contract still demands a finding. That combination is not hypothetical — it is the *second* false finding trace `5d6c9ca05d7c6ce12e41a84980693f10` produced, after the slash-command fix closed the first. On that 31-second `/ship` (10 spans, two `git` calls, no failures, no revisits) the review's sole bullet was *"the agent addressed two distinct architectural fixes (Token attribution and Model attribution) in a single session"* — every noun of it lifted from the previous turn's summary of work that had already shipped in an earlier trace, none of it present anywhere in the trace being reviewed. Suppressing the section is the fix; the template's scoping paragraph (the section is for resolving the request, the work it describes is not this trace's and not to be judged, ignore it entirely when the request is unambiguous) is the net under it, because neither alone holds a 7B model. Note the section's own text must not assert *"the request below is a reply to it"* — that is false whenever a turn opens new work, and it was what licensed treating the earlier turn as in-scope. The query writes `attributes ->> 'session.id'` as a literal, not a bind param, because `idx_log_records_session_id_ts` is an **expression** index on exactly that text and Postgres matches index expressions structurally — the same trap V19 documents for `event_name`. Measured with it: 0.08 ms, 8 buffers. It runs once per regenerate, never on a dashboard read path. `assistantResponseEventName` / `responseAttribute` were added to `TuningProperties` (and the catalog, as `NOT_MIRRORED`) for this: the event name is now read from configuration on both sides rather than living as a literal in the builder.

**A request that names a user-visible surface has named its target, and the review had no way to know that.** `wordingAlreadySettled` gets a third code-side verdict, `requestIsQuestion` — the request's stripped text ends in `?`. The template has always said a question "is not underspecified for being open ... it has no target to name, so neither fault below applies to it", so this is not new policy; it is that rule moved out of prose because prose lost. On trace `8f98bde5c347e9844362370f41f1c5ac` the request was *"On the settings page for Ollama section can the models available be listed in a drop down?"* and the `Better wording` line came back telling the reader to *"specify the scope by listing the files that need modification (e.g. `SystemController.java`, `OllamaClient.java`)"* — files that trace existed to discover. **Three fences lost at once**: the question rule, the "a short instruction is not automatically an underspecified one" rule, and the second call's "use only what the reader could have written before that trace ran". **The structural half is why.** The only other route to a settled wording without a preceding question is `requestWellAimed`, which fires off `directedStartObservation` and therefore requires the request to name a **file** — measured over 30 days and 692 human-written non-slash prompts, only **34 (4.9%)** name a file at all. So 95% of real requests reached section B with the "unnamed target" fault live and the one remedy it knows how to write pointing at paths the reader never had. **The mark was never the rule, only the available proxy — the gate now also reads an interrogative first word.** A writer can simply omit the mark, and this one routinely does; what the gate asks is whether the request poses a question rather than naming work, which an opening question word answers as directly. Measured over 30 days and 751 human-written non-slash prompts: ending in `?` gates 156 (20.8%), and adding `QUESTION_OPENERS` takes it to 209 (27.8%). Per opener in that window — `can` 15, `what` 14, `how` 6, `does` 5, `is` 5, `should` 4, `why` 3, `will` 1; `could`, `would`, `did` and `are` matched nothing and ride along for coverage, each being unambiguously interrogative in opening position, which is the bar for the list. **Bare `do` is deliberately off it while `does`/`did` are on**: it was the single opener whose matches were imperative, and all five were ("do 1 and 2", "do a code review on uncommitted changes", "do fix 1 and fix 2", "do not automatically add changes to git", "do not use any 70b models"). `any` was dropped for the same ambiguity ("any way to …" asks, "any changes should …" instructs) with no measured matches to justify the risk. Matched on the **first word only**, for the same reason the mark is required at the end: "fix the cache-read total, can you" is an instruction with a question word in it. The residual false positive is the polite instruction — "can you close all those dependabot alerts", "can you create a full pg_dump" — about 6 of the 53 added (11%), since `can/should` + `you/we/i` is genuinely mixed ("can i see the full example data" is a real question). Accepted on the reasoning the `?` half already uses: wrongly gating an instruction costs one wording tip, while wrongly failing to gate a question produces the "unnamed target" advice this whole paragraph exists to stop. **Trace `9ab1feeebdd15a449bbc4c9983dcb79d` is what forced it.** Its request "can the phase timeline be condensed any" is a yes/no question the agent answered "Yes — there's meaningful headroom", resolving the target on its first tool call in 755ms of a 75s trace; with the mark absent the gate stayed shut, and on one regeneration **all three findings were restatements of its supposed vagueness**, two of them quoting section B's own bullet names ("unnamed target", "ambiguity that cost work") back as findings, with an `Instruction rule` telling the reader to add file paths to their prompts — advice no agent reading `CLAUDE.md` can act on. **Ends-with the mark, not merely contains one, and no length bound**: ends-with excludes a long instruction carrying a parenthetical aside, narrowing 165 matching prompts to **149 (21.5%)**; a length bound was considered and rejected on the data, since the 49 questions longer than 120 characters read as genuinely as the short ones (the ≤120 gate earns its place in `answersPrecedingQuestion` for a different job, spotting a terse *reply*). Cost of the residual false positives is near zero — the few instruction-shaped questions in the sample name their target exactly — and only the wording half is suppressed, leaving drift and sections A/C open. It deliberately adds **no** `Went well:` positive, unlike its two siblings: asking a question is not wording doing a job worth crediting, and positives are gated harder than faults precisely because praise is the easier thing to fabricate. Both templates were fixed alongside it, since the verdict only suppresses the fault on 21.5% of traces and the remedy has to be safe on the rest: **never advise naming a file, class or module unless the request shows the reader already knew it.** The apply-this template's own exemplar was the licence for the bad advice — it read *"'Name the file: say `fix the cache-read total in MetricPointRepository` rather than `fix the token thing`' is the shape"*, teaching the model that naming a path **is** the canonical shape of good wording advice. Same trap as the hedging examples that got quoted back as the user's own words; the exemplar now demonstrates the comparison shape using a scope the reader plainly had.

**Rendering the preceding turn was not enough, and the second half of the fix is a code-side verdict.** On trace `83b37f35664d88848e00d20be9f737ae` everything above worked — the previous message ended *"Want me to fix `model` the same way — …?"*, the request was *"yes fix it"*, and the prompt carried both the scoping paragraph and section B's "a request that answers the preceding message is NOT ambiguous on that ground" line — and the review still reported *"the user prompt 'yes fix it' is too vague and allowed the agent to wander"*, spending its wording line (then `Rewritten request:`, now `Better wording:`) re-specifying, in the reader's place, work the reader had just been asked a yes/no question about. Two prose fences in one prompt lost to a three-word request, which is the same lesson `buildObservations` is built on: decide it in code, hand the model a verdict, don't hand it an instruction and hope. `answersPrecedingQuestion` is that verdict — the request is at most 120 characters **and** the *rendered tail* of the preceding turn contains a `?` — and when it holds, the two wording bullets (`Unnamed target`, `Ambiguity that cost work`) are removed from section B outright rather than qualified, the section says the wording question is settled and not the model's to re-decide, `Better wording:` is pre-answered `None`, and a `Went well:` observation states the request was an answer rather than an ask (so `hasPositiveObservations` gives the request half somewhere true to land instead of manufacturing a fault). **Drift deliberately survives** — going somewhere the exchange never invited is a real fault whose fix is a standing rule, not a rewording. Both halves of the gate are measured over 30 days and 758 human-written non-slash prompts: **470 (62%) are ≤120 characters**, so length alone would suppress the wording half on nearly two thirds of traces; pairing it with the question mark narrows it to **129 (17%)**. The `?` is looked for **anywhere in the tail, not at its end** (99 prompts, and it would have missed this very trace, whose question is followed by a qualifying sentence), and in the **tail rather than the whole response**, because the tail is the only part the model is shown — a question 8k characters above it explains nothing the reader can verify.

**A request with no target and no question can still be settled, and the evidence for it is the trace's own execution rather than the wording.** `requestWellAimed`, `answersPrecedingQuestion` and `requestIsQuestion` are the only three routes into `wordingAlreadySettled`, and all three read the *request*; none of them can fire on an ordinary bug report that names no file and asks nothing — *"when toggling to disabled the save button is disabled too"*, the real request on trace `24e1af7c5582529fe62dcacabe2d0a23`. That trace is nine calls, one coherent thread — `Bash grep` the bug, `Read` the file, two `Edit`s fixing it and its own adjacent doc comment, two more `Bash grep`s and a `Read` checking whether the same stale claim exists elsewhere, one more `Edit` fixing the doc it found, a `Bash` verification run — no failure, no revisit, every edit following a read or search of the exact file it touched. The review it actually produced faulted the wording anyway: *"leading the agent to perform multiple, sequential, and overlapping tasks ... instead of focusing on a single, actionable fix."* Every one of those calls traces back to the one reported bug; updating the doc comment and `CLAUDE.md` is fixing the stale docs that made the same now-corrected claim, not "overlapping tasks" — and the trace's own shape already proves it, without needing a fourth route into the wording verdict that would also silence "Unnamed target" (a bullet that states a true fact about this request, just not a fault). `focusedResolutionHolds` is a narrower, independent flag that suppresses only **"Ambiguity that cost work"**, leaving "Unnamed target" and drift open: every `MUTATING_TOOL_NAMES` call must be preceded, in the same branch and within `FOCUSED_RESOLUTION_CHAIN_WINDOW_CALLS` (15) calls, by a `SEARCH_TOOL_NAMES` (`Read`/`Grep`/`Glob`) call against the identical file; nothing in the trace may have failed (`isFailedToolCall` or `modelCallFailureFor`); and `revisitedFiles` must report nothing at all, since a re-read or re-search with a different input is exactly the "different intent" this verdict has to exclude. Measured over 30 days against every human-written, non-slash, non-notification request that `requestWellAimed` does **not** already clear (1,497 traces): 1,276 (85.2%) show no failed tool call anywhere; of those, 597 made at least one file-addressed mutating call; of those, only 222 (37.2%) are also free of a `revisitedFiles` group; and of those 222, only **113 — 18.9% of the 597, 7.5% of the full 1,497** — have every mutating call reachable within the 15-call window, a rate in the same range `requestWellAimed` (4.9%) and `requestIsQuestion` (21.5%) already clear before either is allowed to remove a fault from the model's reach. The 15-call window itself comes from the same data: among mutating calls that DO have an earlier same-file search anywhere in their trace, the gap between the two sits at p50 6 / p75 17 / p90 41 calls, so 15 sits just under the p75. **Drift deliberately does not read this flag.** The verdict is entirely internal to the trace's own execution — it proves the agent never wandered, failed, or doubled back — and says nothing about whether the file it landed on was the one the request was actually about; a tight, revisit-free chain of edits on the *wrong* file is exactly as "focused" by this test as one on the right file, and that mismatch is precisely what drift exists to catch. `TraceAnalysisPromptBuilderTest` pins both the trace's own reproduced shape (suppresses ambiguity, leaves "Unnamed target" open) and the negative case a suppression gate needs most — a mutating call on a file nothing before it read or searched must not get the benefit of the doubt.

**An observation the code has already decided is not a fault is dropped, not annotated — that is the single clearest result of this whole line of work.** Every fence that removed something from what the model could see or emit has held across runs (the `wentWell` schema gate, the withheld rule, the dropped target, the deduplicated error line); every fence that left the wrong answer visible and argued against it in prose has failed on a 7B model — the outlier twice, the approval wait once, each time with the `Not a finding:` note sitting right there in the prompt. `NOT_A_FINDING_PREFIX` survives for the case it was built for, an environmental **failure**, where the reader genuinely needs to see that the call died and only the verdict is in question. It is not the tool for an observation whose entire content is "this was fine". **Detection is done in code and handed to the model as "Verified observations"; the model is only asked to judge.** Measured directly against a real 60-call trace with both small models this feature targets, asking them to find patterns by scanning the timeline produces confident, wrong citations: llama3.1 reported "calls 21 and 26 are identical TodoWrite" when 21 and 26 are *model* calls and the TodoWrites are 20 and 25; qwen2.5-coder said "call 7 is identical to call 1" when call 1 is a model call. Both, however, explained a fact correctly the moment it was handed to them pre-computed. So `buildObservationLines` computes the revisited files, the failed calls (each named with its tool), the failed *model* calls (grouped by status code and message — see the environmental-failure note below), the shell-antipattern calls (reusing `TuningProperties.bashAntipatternReplacements`, keyed on the command's first token like `ReportService` does, read off the span's `full_command` — present on 100% of measured Bash spans), the outlier model call, the cost drivers (a dominant sub-agent, a call taking ≥25% of spend across ≥4 calls), poor cache reuse, and the two context-size shapes; the template presents them as accurate and tells the model to start there. Re-running the same trace after this change, every citation in the output was correct. **Do not "simplify" this by deleting the observations and trusting the instructions** — that is exactly the version that fabricated. Note `grep` is deliberately absent from the antipattern map (it is shared with the markdown report and is a catalogued `tuning.*` property), so Bash `grep` is not flagged even though AGENTS.md prefers the Grep tool; changing that map is a report-wide decision, not a prompt-local one.

**A few observations say what the trace got RIGHT, and they are gated harder than the faults are.** They carry a `Went well:` prefix and the template promotes them into a third answer section, `**What went well**`, ahead of `**What went wrong**`. The reason is not balance. This review's documented failure mode is *manufacturing* a fault on a trace that has none — trace `5d6c9ca05d7c6ce12e41a84980693f10`, a 31-second `/ship` with no failures and no revisits, produced two separate fabricated findings before the slash-command and preceding-turn fences went in — and an answer contract with nowhere to put anything but criticism will produce criticism. A verified positive gives that output somewhere true to go. The gating exists because **praise is easier to fabricate than criticism**: nothing constrains it, so an ungated "what went right" is the same non-finding the outlier-model-call line was before it was gated, firing on every trace and saying "the agent used Read appropriately". So there is deliberately **no positive for healthy cache reuse** (the median trace already reuses 96.8%, the overview says so, and `cacheReuseObservations` reports only the bad direction) and **none for a clean trace** (that is already the answer contract's one-sentence empty case). Exactly two shapes qualify, both carrying information no dashboard page and no section of the markdown report gives the reader:

- **A directed start** (`directedStartObservation`) — the trace's **first** tool call opened a file the request names, so nothing was spent finding the target. This is the honest inverse of section B's "unnamed target" fault, and the only thing in the feature that tells a reader their *wording* worked. Three constraints keep it from becoming the ungated line: it reads the first tool call **only** (a match on a later call proves nothing, since whatever ran before it is exactly the searching this claims did not happen — so a first call carrying no `file_path` ends the check rather than scanning on); it matches the file's **last path segment**, because a reader writes `TraceService.java` while the span carries the repo-absolute path; and that segment must clear `MINIMUM_NAMED_TARGET_LENGTH` (5) so a short name cannot match inside an unrelated word. It is fed `promptText` only when `hasPrompt` — never a slash command, a `<task-notification>` envelope, or a subagent run — so it cannot credit wording nobody wrote, the same fence `slashCommandName` / `isMachineAuthoredPrompt` put on the fault half.
- **A subagent that earned its cost** — an indented `Went well:` qualifier on the existing dominant-subagent observation, emitted when the main loop's own peak context was ≥ `LARGE_STARTING_CONTEXT_TOKENS`. The template has always said a dispatch that keeps a long search out of the main context is money well spent, but only as a hedge hanging off what still read as a criticism. When the main loop was measurably that loaded, the hedge is a fact, and stating it as one is what lets the answer report the dispatch as the right call. It rides on the observation it qualifies rather than becoming a second line, so one dispatch is never reported twice.

Three template-side rules hold the section honest, and all three are pinned by tests: the section renders **only** when a positive was computed (`hasPositiveObservations`, which also switches the contract's "write exactly the two/three sections" count), it is capped at two bullets drawn **only** from `Went well:` lines rather than from the model's own impression, and a positive **feeds none of the three `Apply this` lines** — "keep doing X" is not a usable standing order, and rule 3's "every finding ends in a change" carries an explicit carve-out saying so. `max-prompt-chars` went 32000 → 33000 for this (and later to 36000, for the timeline's sake rather than the instructions'); every added block is conditional, so a trace with no positive pays nothing.

**The review has to end in something the reader can apply, and the two halves of that are split by who can do them.** The code half: an observation whose remedy is *mechanical* carries its own pre-written `Suggested rule:` line — a shell antipattern (``Default to Glob instead of `find` in Bash.`` — phrased as a default rather than a ban because one template serves the whole `bashAntipatternReplacements` map and only some of its entries are total substitutions; see `ShellAntipattern`), a revisited target (Read gets a rule about reading a file once at the length you need; every other tool gets the general form, since the Read wording reads as nonsense on a repeated `Grep`), and a request begun on an already-loaded context (start unrelated work in a fresh session). A failed call deliberately carries none: its fix depends on why it failed. Nor does a dominant sub-agent — one that kept a long search out of the main context was money well spent, and the template says so rather than letting a big number read as a fault. The model half: the template's answer contract requires every finding to end in `Fix: <one concrete change>` and requires the answer to close with an **Apply this** section of exactly three lines — `Instruction rule:`, `Tool swap:`, `Better wording:` — each either text the reader can use as it stands or the single word `None`. **Only two of those three are paste-ready, and the third was renamed because pretending otherwise made it useless.** A rule goes into a CLAUDE.md and changes every trace after it; a tool swap is a standing correction. The wording line is about a request that has *already run* — the reader is looking at this trace precisely because it finished — so a `Rewritten request:` "ready to paste, built from the real words of the request above" offered them a copy button whose only effect would be re-issuing finished work. Its value was always instructional, so it is now `Better wording:`: the words that cost the agent work and what to say instead, in one or two sentences, rendered by the frontend *against* the request it is about rather than as a thing to copy. **The 'before' half of that comparison is stored, not generated** — `trace_analyses.user_prompt` (`V24`), written at generation time from `TraceAnalysisPromptBuilder.judgedPromptText`, which is the same gate `build`'s own `hasPrompt` uses (`isJudgeablePrompt`), so the card can never show a "before" the review was not actually given, and a slash command or `<task-notification>` stores null exactly where the review drops section B. Having the model quote the request back instead would put the one half this application can supply verbatim into the half the contract already spends a rule policing ("Never invent prompt or response wording"). It is stored rather than re-read because `getStored` fires on every dialog open and is deliberately one cheap `MAX(end_timestamp)` probe. **A `Better wording:` line that only repeats a fault's own `Fix:` is rendered `None`.** The second call is handed the findings and asked to distil them, and it distils by copying: on trace `adae1753270dd3088520435ae7f8af94` the line came back byte-identical to the first bullet's `Fix` on two consecutive runs, so a three-bullet review spent one of its three Apply-this slots restating a sentence the reader had just read. `TraceAnalysisAnswer.betterWordingUnlessAlreadySaid` drops it, on exactly the argument `collapseDuplicatedBlock` already makes — removing a byte-identical repeat can never take away text the reader has not already been shown. Matched on normalized text (trailing sentence punctuation off, case-folded, since `sentence()` adds punctuation on one path and not the other) and no looser: a wording line that merely *overlaps* a fix is still doing its own job. **The frontend still parses the legacy `Rewritten request:` prefix**, for the same reason it still parses `CLAUDE.md rule:` — stored analyses are re-read, not migrated. **`Instruction rule:` carries a target**, written `<target> — <instruction>`, because a rule that belongs in a skill's own definition is useless written against `CLAUDE.md` and vice versa. The target is a **closed list built from evidence** (`putSkills`): always `CLAUDE.md`, plus `skill:<name>` for each skill this trace shows actually ran *and* whose `skill.source` is `projectSettings`. A `bundled` skill ships with Claude Code and is not the reader's file to change, so it is never offered — and free-form targets are never allowed, since a model that cannot see the repo invents plausible paths that do not exist in it. **Editable skill targets are listed ahead of `CLAUDE.md`, and the template names the skill as the default.** The choice between them originally rested on one trailing clause of prose against a list that opened with `CLAUDE.md`, and a small model takes the first, most general option: on trace `5d6c9ca05d7c6ce12e41a84980693f10` — a `/ship` run where every call was made while the project-defined `ship` skill was in force and `skill:ship` was on the list — both findings were about that skill's own behaviour and the rule still came back against `CLAUDE.md`, where it would fire on every unrelated trace in the repo and not on the one file able to act on it. `putSkills` now appends `PROJECT_INSTRUCTIONS_TARGET` last and sets `hasEditableSkillTargets`, which gates a template rule that defaults to the skill and demands a reason to widen ("if you cannot say why the rule should fire on unrelated work, it is not a `CLAUDE.md` rule"); a trace with no editable skill is told plainly that `CLAUDE.md` is its only target rather than being offered a default it cannot follow. Ordering and wording are each half the fix — the `CLAUDE.md`-first list beat the prose for as long as it led. **A third target, `PERMISSIONS_TARGET` (`.claude/settings.json`), is offered only when `blockedOnUserObservation` fired.** The pre-written rule that observation carries ("Pre-authorize or batch the permission prompts…") is not one any instructions file can act on — pre-authorising a tool call is a permissions setting the harness reads before it asks, not an instruction the agent reads — so on trace `adae1753270dd3088520435ae7f8af94` it came back as `Instruction rule: CLAUDE.md — Pre-authorize or batch the permission prompts…`, advice the reader could not follow in the file it named. Same unfollowable-remedy shape as telling a `<task-notification>` continuation to start a fresh session. It is **evidence-built, never a standing option**, for the reason the whole list is: a trace that never waited on approval has no rule for it to carry, and offering it anyway invites exactly the invented-path failure the closed list exists to stop. It sits **behind the skills and ahead of `CLAUDE.md`** — ahead of the comparison it has to win, behind the one that took an ordering *and* a template rule to get right, so this cannot disturb the skill default — with a `hasPermissionsTarget` template block naming which rule it is for and saying it is for no other. Because the list now depends on an observation, it is resolved **once** in `build` and travels on `ApplyThisInputs.ruleTargets` as values rather than being recomputed for the schema enum: `ruleTargetsForTrace` was deleted outright, since a second computation in `TraceAnalysisService` would have been a second implementation of that gating — free to offer the model an enum the prompt never named, the same drift `TraceCallNumbering` exists to prevent. The frontend parses the target off the line and renders it as a chip (`AnalyzeTraceDialogView`'s `splitTarget`); it also still accepts the **legacy `CLAUDE.md rule:` prefix**, because analyses are stored and re-read and every row generated before targets existed would otherwise lose its card — don't drop that alternative without migrating or expiring `trace_analyses`. Asked to invent project-instruction wording, a 7B model writes vague wording; asked to decide whether a ready-made rule applies and to copy it verbatim, it decides well. **`Tool swap:` is settled in code, not asked for.** It is the one Apply-this line whose content is fully determined by evidence already computed: the shell-antipattern observation holds the command and the tool that replaces it, so `ShellAntipattern.toolSwapLine` composes the line, it travels on `ApplyThisInputs.settledToolSwap`, the second call's template is told it as a decided fact, and `TraceAnalysisAnswer.of` **overrides** whatever the model returned. The override is the point rather than a fallback. On trace `9ab1feeebdd15a449bbc4c9983dcb79d` — 5 of 10 Bash calls were `sed -n <range>p` used to read files — the observation fired with its pre-written rule, `suggestedRulesOf` repeated that rule to the second call under "Ready-made rules", and the answer still came back `Tool swap: None`. Nothing was wrong with the second call's contract: it is gated on "only when the review actually reported a tool being used where a dedicated one exists", the **first** call's prose had dropped the observation, and `None` followed correctly from what it was shown. That is the failure this line's placement makes unreachable — a fact can survive being in the prompt twice and still be lost, because the second call cannot see the trace and can only distil what the first call chose to keep. Kept deliberately narrow: it settles that one line and touches neither `instructionRule` nor `betterWording`, both of which are judgments about which fault matters most. When several commands fire, the one with the most calls behind it wins (insertion order breaking ties) since there is only one line; the rest keep their own observation and `Suggested rule:`. **The prose path is not covered** — the template branch tells it the line, but nothing enforces it there, since only the structured path has a field to override. **The outlier model call is gated, and that gating is the point.** The observation was previously an unconditional "Longest model call: call N at M ms" — every trace has one, so it fired on every trace with nothing to compare against, and what came back was the exact non-finding this review exists to kill: *"call 130 at 52333 ms was the longest model call ... it's unclear whether this was necessary."* Duration alone cannot settle it; output tokens can (a long call with a lot of output was writing, which is earned; with little output it was deciding, and the fix is to leave it less to decide). So the line now needs ≥3 model calls, ≥2.5x the trace's own median and ≥15s absolute, and carries the output tokens and the median it is measured against — or is dropped rather than manufacturing a finding. **Whether a surviving outlier is a fault is also decided in code, and moving that verdict out of the template is the second half of the same fix.** The template used to hand over the numbers plus a two-clause rule ("many output tokens means writing, which is earned and not worth reporting; few means deciding"), which is exactly the shape `buildObservations` exists to refuse — and it failed the same way: on trace `adae1753270dd3088520435ae7f8af94` the outlier produced **4,676 output tokens, the most of any call in that trace** and 1.8x the next highest, and the review reported it as *"excessive reasoning for the task at hand"*, reading the rule backwards and spending a bullet on the trace's single largest piece of writing. **The discriminator is the rate, not the volume**, because volume cannot separate the two cases: measured over 30 days, the slowest call's output against its trace's median output is p10 **3.37x**, so "produced a lot" is true of essentially every outlier and decides nothing. Milliseconds per output token separates them sharply — against its own trace's median rate the outlier sits at p50 0.88, p75 1.00, p90 1.05 (normally *as efficient* per token as the typical call, just longer because it wrote more), while **10 of 351 (2.8%)** sit at or past 2.0x with **nothing at all between 1.2x and 2.0x**, so any floor in that gap scores the same ten traces and `MODEL_CALL_DECIDING_RATE_MULTIPLE` takes its conservative end. Below the floor **the line is dropped entirely**; at or above it, it stays an ordinary fault. It was annotated rather than dropped at first — the line plus a `Not a finding:` note saying its length was earned — and phi4 opened a fault about it anyway on two consecutive runs. Dropping matches what this method already does when no call stands out at all, so the excused case stops being a third state. **Zero output tokens is the extreme deciding case, not an unmeasurable one** — a long call that wrote nothing spent all its time deciding — and a trace with no usable median rate is likewise left as a fault, since this branch suppresses findings and "cannot tell" must never be the branch that suppresses one. Two template consequences: section A's bullet now says the verdict has been made rather than restating the rule (and deliberately avoids the literal `Not a finding:` string, which would otherwise appear in every prompt's fixed instructions and make `hasNotAFindingObservations`' explanatory block incoherent on traces carrying no such line), and that block's own sentence was widened from "something the environment did" to cover both shapes it now marks. **An approval wait that is one pause is not a pattern, and gets no rule and no target.** `blockedOnUserObservation`'s total reads as a run of interruptions whatever shape the waiting really had: on trace `adae1753270dd3088520435ae7f8af94`, **23m 25s of the 25m 47s sat in a single pause at call 30** and the review reported six calls as an even pattern of "inefficient user interaction" and prescribed batching — a remedy for a problem that trace did not have. `singlePauseDominates` (`BLOCKED_ON_USER_SINGLE_PAUSE_DOMINANCE`, 0.80) gates three things together: the whole observation is dropped, the pre-written batching rule with it, and `PERMISSIONS_TARGET` comes off the rule-target list — so such a trace is offered no observation, no ready-made rule *and* no file to put one in. The per-call `[blocked Ns on user approval]` markers stay on the timeline, so the fact survives where it is unambiguous: on the call it happened to. This too began as an annotation and lost the same way — phi4 faulted the wait and *invented* a batching remedy with no rule offered. When the observation does render, it names the longest wait **and its call number**, because given only a total and six call numbers the model wrote "a long pause of 23m 23s at calls 4, 6, 30, 46, 48, 50", attributing one pause to all six. Measured over 30 days across the 154 traces where the observation fires, the largest single wait as a share of total blocked time is p10 0.34, p25 0.48, p50 0.72, p75 0.98, with **65 of 154 (42%)** at or above 0.80 and 48% having only one wait past the 10s floor at all; there is no gap to aim at, so the floor is set on meaning — at 80% the one pause *is* the waiting. **One tool failure is one error line.** `buildErrorLines` counted each twice — once on the `tool.execution` span and once on the `tool_result` log describing the same failure — and the two `ErrorLine` keys differ only in `source`, so they never collapsed; the same trace rendered one Bash failure as two lines and an outcome reading `1 error (2 distinct)`, where "distinct" exceeded the total it qualified. The span leg now skips `toolExecutionSpanName` (the log is the richer of the pair and the span derivative; `llm_request` spans have no log counterpart and still contribute), and the `(N distinct)` clause only renders when it **narrows** the count. The failed-call observation also carries its error text now rather than leaving it in the Errors section — a bare `40 (Bash)` says something failed but nothing about what, and that trace's only failure went unmentioned across three runs. `TraceAnalysisService.collapseDuplicatedBlock` is the net under the "write each heading once and stop" instruction: a real answer wrote its whole review, then the same review again word for word, then a closing paragraph. It removes only a **byte-identical** immediately-repeated block of ≥200 characters anchored on the answer's own first substantial line, so it can never delete text the reader has not already been shown — anything looser (near-duplicate matching, truncating at a repeated heading) risks eating a real finding, which is the worse failure. The instructions are a fixed ~10.5k characters of every prompt, which is why `ollama.max-prompt-chars` is **36000**: it was raised from 24k for the answer contract and from 26k for the cost/context section, the spend split and the preceding turn — each time so the instruction growth came out of headroom rather than out of the trace's own timeline, which is the section with nothing to spare. The last raise, 33k → 36k, was arithmetic rather than a judgment call: `OllamaClient.contextTokensFor` sizes `num_ctx` as `promptChars / 3 + 1 + 4096` clamped to `contextTokens`, so 36,000 gives 16,097 against the 16,384 ceiling and 36,861 is the first value that would clamp — 36k is the largest cap the already-allocated window holds, and it cost no KV-cache RAM. Anything past it means raising `contextTokens` too, or Ollama silently left-truncates.

**The dialog's "what happened" recap (`trace_analyses.summary`, `V26`) is composed in code by `buildTraceSummary` and is never sent to Ollama.** Every other piece of prose this feature produces is judged output with a `Fix:` behind it, or a verified fact traceable to a call number; a narrated retelling has neither property and is exactly the shape the documented failure mode hits hardest — `buildObservations`' javadoc records a small model calling two *model* calls "identical TodoWrite tool calls" when merely asked to describe what it saw. So it is arithmetic and string concatenation over facts already computed for the overview and the timeline, in the same spirit as `formatDuration`. **Its detail is one labelled line per question, not clauses of one sentence.** An earlier revision packed which files were touched, which subagents ran, which skills were in force and what it all cost into a single `Work:` sentence, which is the form that hides them: the reader is asking "what did it lean on", "where did the money go", "did it compact" one at a time. So `Work:` is now the at-a-glance shape alone (tool calls · model calls · duration) and the detail is `Tools:` (per tool, busiest first), `Models:` (per model, raw ids matching the overview's own list), `Files:` (per file, naming what was done to each — `TraceService.java (Read ×2, Edit)`, first-touch order, capped at `MAX_SUMMARY_FILE_NAMES`), `Cost:`, `Skills:` and `Compaction:`. **A line whose subject is simply absent renders not at all** — a "none" on every trace that never dispatched, compacted or ran a skill is noise; the three lines that always render (request, work, outcome) say so explicitly instead, because for those an absence *is* the fact.

Three details are load-bearing. **The `Cost:` line renders the authoritative trace total first and labels the rest "of which measured".** The total comes from `trace_costs`, which counts every request log stamped with the trace id; the split (main loop, then one clause per `SubagentDispatch`, then auxiliary) comes from `attributeCalls`, which can only place a request that joined a model-call span on `request_id`. **The parts are not guaranteed to sum to the total and must never be normalised to it** — that would invent an attribution the data does not support, the same trap the two-pipelines note above warns about for tokens. Each dispatch clause carries its dispatch call number, which is the only thing telling two dispatches of one agent type apart (Claude Code names every project-local agent `custom`). **The `Compaction:` line reads the trace-correlated `compaction` log event** (`TuningProperties.compactionEventName`), not `api_request` rows whose `query_source` is `compact`: the event carries `trigger`, `pre_tokens`/`post_tokens` and `duration_ms`, and is stamped with the trace id. It **also fires for a compaction that died** (`success=false`, with an `error` — 2 of 8 on the live database), so `success` is read rather than the event's presence taken as a completed pass; an aborted compaction spent the time without reclaiming the room, which is the worse outcome and the one most worth surfacing. An absent `success` is unknown, not a failure. **The clause separator is a middle dot (`SUMMARY_CLAUSE_SEPARATOR`), never a comma**, and it is the one thing the dialog splits a line into bullets on. A comma split shredded the two free-prose lines — the quoted request and the quoted final message — into bullets mid-sentence, and would now also cut a file away from its own `(Read ×2, Edit)` tool list, which is why that nested list is the one place a comma is still used. Stored analyses are re-read and never migrated, so a summary written before the separator changed simply has no dot in it and renders one line per fact; both paths are pinned by tests on each side.

**Revisit detection is keyed on the execution path, not just `(tool, file_path)`, and that is a correctness fix.** A trace is a **wide, shallow tree**: the main loop plus N sibling subagent dispatches, each owning the subtree under its `tool.execution` span. Measured over 90 days, fan-out reaches **15 dispatches in one trace** (avg 2.43 when present) while nesting is **0 of 291** — no dispatch has ever run inside another. Grouping revisits across that tree reports the main loop reading a file and a subagent later reading the same file as one "touched 3 times" finding, but a subagent runs in its own fresh context and keeping a long read out of the main one is the *reason* to dispatch it. **277 of 1,812 revisit groups (15.3%, across 59 traces) crossed a branch this way.** The rate understates the damage: this is the observation carrying a pre-written `Suggested rule:` line the answer contract tells the model to copy verbatim, so a false grouping became a false standing rule in the reader's CLAUDE.md — the most confident way for the review to be wrong. `revisitedFiles` therefore takes `CallAttribution` and keys on `(branchKey, tool, fileName)`; two *different* subagents each reading one file is likewise not counted, since that is a question about how the dispatches were scoped and the rule this observation carries would be the wrong fix for it. Failed calls and shell antipatterns stay grouped **across** branches — a failure is real wherever it happened — but their call numbers carry ` in subagent <name> (dispatched at call N)` when they weren't the main loop's, so a finding lands on the right actor; a main-loop call number is unchanged. **`enclosingDispatchChain` returns the full chain, outermost first, not the innermost dispatch.** With zero nesting today the two are equivalent, but that is current Claude Code behaviour rather than a guarantee, and the innermost-only form silently collapses `main → Explore → general-purpose` to `general-purpose`, losing who dispatched whom. Aggregation (cost, call counts) still lands on the innermost dispatch — the subagent that actually made the call owns it; the chain above is identity, not ownership. **The timeline is deliberately still one interleaved, trace-ordered list** rather than per-branch sections: call numbers are assigned in trace order and both the observations and the citation contract are written against them, so regrouping is a correctness risk for a legibility gain. Reach for `branchKeyOf`/`branchLabelOf` in any new detector rather than adding a second notion of "which agent did this".

**A write to a file ends its revisit window, and that closes two false-positive shapes at once.** `revisitedFiles` keys on a `generation` that increments whenever a `MUTATING_TOOL_NAMES` call touches the path, so calls only group with calls that saw the same content. Without it the observation contradicted the rule it carries: on trace `adae1753270dd3088520435ae7f8af94` it reported "`LogRecordRepository.java` touched 3 times, at calls 16, 18, 26" while its own pre-written remedy reads "do not come back for another slice of a file you have already read *unless an edit changed it*" — and call 26 followed the Edit at call 20 on exactly that file, so the one call the rule excuses was counted as evidence for it. The second shape is two sequential `Edit`s to one file, which is how an edit normally happens: a mutating tool ends its own window too, so it never groups with the next one. Neither is marginal — measured over 30 days, **676 of 1,203 revisit groups (56%) were on a mutating tool and the window leaves zero of them**, taking the whole population from 1,203 groups over 297 traces to 429 over 165. Every one of those 676 carried a `Suggested rule:` line the answer contract tells the model to copy verbatim, and the general (non-Read) form of that rule reads as nonsense for an `Edit` — "re-read the result you already have instead of running it again" is advice not to make the second edit. The **inline timeline marker** (`[same file, different input, at ...]`) carries the identical window, and calling it a lower-stakes follow-up was wrong: with the observation fixed but the marker not, the very next run of `adae1753270dd3088520435ae7f8af94` wrote its Redundant-work finding — and hung its `Instruction rule` on it — from the **marker**, citing the post-edit re-read the rule it copied explicitly excuses. `targetKey` therefore takes the generation too, fed by a `mutatesTarget` flag set on `TimelineEntry` where the tool name is in scope rather than parsed back out of a label that may carry a subagent prefix. An observation and a timeline marker that disagree are worse than either being wrong alone, because the model picks whichever it read last.

Both markers cap their call-number list at 8 and report the remainder as "and N more" — a measured real trace read one file 69 times with 53 distinct inputs, which would otherwise put 50+ numbers on a single line. `TraceAnalysisPromptBuilderTest` pins both negative cases (different tools on one file, and an exact repeat) alongside the positive one and the cap. **`fileUsageLine` and `revisitedFiles`/`RevisitedTarget` used to group on the bare last path segment, and that was a correctness bug rather than a rendering choice.** Their own doc comments said so explicitly — "named by its last path segment" — on the reasoning that a reader names `TraceService.java`, not the repo-absolute path. What they missed is that this repository guarantees two *different* files sharing one basename by construction: it keeps a `CLAUDE.md` per `pages/<Name>Page/` folder, plus root-level ones. Verified directly against trace `df8c757de3bfbfe9c1da2b29f431a192`: `frontend/CLAUDE.md` was read once (that trace's call 52) while `frontend/src/pages/TraceDetailPage/CLAUDE.md` was read 5 times and edited 4 times, all on one branch — a genuinely redundant re-read pattern, real and worth flagging — and the basename-only grouping merged the two into one false "`CLAUDE.md` (Read ×7, Edit ×4)" fact in the code-composed `Files:` line, and a matching false "re-read `CLAUDE.md` at calls 52,53,55,190,196,204" observation in `revisitedFiles`, carrying a `Suggested rule:` line the answer contract tells the model to copy verbatim into the reader's own `CLAUDE.md`. One of those six call numbers (52) names a wholly different file. Both now key on the **full path** — correctness — while rendering through a new `disambiguatedFileLabel` helper that shows only the last **two** path segments (`TraceDetailPage/CLAUDE.md` versus `frontend/CLAUDE.md`) — cheap (~15-20 extra characters per line), deterministic, and enough to disambiguate this repo's actual collision shape (a per-page `CLAUDE.md`, an `index.ts` barrel) without either printing the whole repo-absolute path (this file's own reasoning: ~80 characters per line of pure path noise) or standing up a two-pass "only widen the names that actually collide" scheme. `directedStartObservation` was checked against the same bug and is unaffected — it inspects only the trace's first tool call, never aggregates across files, so no basename collision is possible there. **`TraceAnalysisAnswerScorerTest`'s `fileCitationViolations` case, added alongside this fix, is built from a synthesized minimal prompt reproducing the same shape** (two Read calls touching `AnalyzeTraceDialogView.tsx` and the sibling `AnalyzeTraceDialog.tsx`) because the checker's own citation-matching had an independent bug on the very same trace — see the `TraceAnalysisAnswerScorer` paragraph below. **A `user_prompt` record is not automatically a human-written prompt.** The harness delivers a `<task-notification>` envelope when a background subagent finishes, and it lands on a `user_prompt` log like any other — 101 of 773 (13.1%) over 30 days. Feeding one into the prompt-quality half asks the model to critique the wording of a machine-generated status message, which is exactly what produced a fabricated *"the prompt said 'I'm not sure if this is the right file'"* finding on a trace whose prompt was an envelope. `isMachineAuthoredPrompt` rejects those so such a trace degrades to the execution half, mirroring `frontend/src/lib/promptSummary.ts` — including its **starts-with** test, since a human prompt that merely quotes an envelope is real text worth judging. Keep the two in step. **A slash-command invocation is the second shape of the same bug**, and `slashCommandName` rejects it the same way: `/ship` is five characters standing in for a skill definition that lives in a file the trace does not carry, so judging it as wording is judging a name. Detected by `command_name` being present on the `user_prompt` (57 of 796 prompt-bearing traces over 30 days; 51 of those ≤30 characters). This is not a hypothetical: on trace `5d6c9ca05d7c6ce12e41a84980693f10` the review reported *"the user prompt `/ship` is too vague, forcing the agent to infer the necessary final steps"* and its one actionable output was a rewritten request (that line's older shape) replacing the command with three literal git commands — advice to abandon the skill the command exists to invoke, with an invented commit message and branch name. The command is still shown to the model, in its own "How this trace was started" section, because the execution half needs to know what started the trace; what's dropped is only section B.

**A failed model call is an observation of its own, and its HTTP status is what decides whether it is a finding at all.** `buildObservations` used to increment the call counter for an `llm_request` span and `continue` straight past it, before the failure check — and `isFailedToolCall` is a `tool_use_id` join, so it could never have covered one anyway. On `80e62a90dc49cec593af52f698d8dd6b` that left the trace's dominant event invisible to the reviewer: **8 model calls inside a `code-review` subagent died on HTTP 429 `"Usage credits are required for this model."`**, and the review came back with four unrelated faults, none mentioning them, plus an invented `halt and report the failure before proceeding` rule for the three *Bash* failures it could see. `modelCallFailureFor` reads the span directly (`error`, `status_code`, and the error status — a model call carries all three itself, unlike a tool call) and groups by `ModelCallFailure(statusCode, message)`, so eight identical deaths are one observation naming eight call numbers. **The classification is by status code, not by "it was a model call":** 429, 408 and every 5xx are the environment refusing the call and get a `Not a finding:` line; a 400 is the agent asking for something malformed, which a rule genuinely can prevent, so it stays an ordinary fault. A **missing** status code is unclassified, not excused. The `Not a finding:` prefix is deliberately not a `Suggested rule:` reading `None` — that prefix is copied verbatim into `Instruction rule:`, whose `<target> — <rule>` shape the frontend parses, so prose there would land in a slot expecting a target. `hasNotAFindingObservations` gates the template paragraph explaining the prefix, and is read back off the rendered lines rather than threaded out of `buildObservations`, since "a line carries that prefix" is the flag's truest definition.

**The Errors section collapses repeats and names its sources, because eight identical sentences read as noise.** `buildErrorLines` keys on `ErrorLine(source, message)` and renders `- llm_request (claude-fable-5, HTTP 429) ×8: Usage credits are required for this model.` — previously eight bare copies of the message with no source, no model and no status, which the reviewing model skipped wholesale. **The status code was previously dropped everywhere**, including `renderLlmRequestLine`; it is now rendered there too, but *only alongside an error*, since on a successful call it is a constant 200 and pure prompt weight. The template's Errors section carries the matching fence — an environmental failure earns no rule, no tool swap and no wording advice, and a repeated one is not the agent doing something wrong N times — while section A's recovery bullet was widened to cover failed model calls, because what the agent did *next* is still fair game.

**A `<task-notification>` trace is a continuation, and gets a section saying so.** Dropping section B (above) stops the review judging the envelope's wording, but leaves the trace reading as a request that arrived from nowhere and then did very little — on `1635329e1e7db7f934b007d90aba7d61`, six spans that grep a test report and report a fix complete. Worse, it resumes a session already deep in a task, so the **starting-context observation fires on a fact that is definitional rather than a fault**, and that line is one of only three carrying a pre-written `Suggested rule:` the answer contract tells the model to copy verbatim: *"start a task that is unrelated to the one before it in a fresh session"* — impossible advice when the notification is about work in **this** session and no fresh session could have received it. `contextSizeObservations` therefore suppresses the starting half for a continuation (the **growth** half is kept: a continuation can still balloon while it runs, and it carries no pre-written rule). Measured over 30 days the line fires on 14 of 96 notification traces (14.6%) against 112 of 685 (16.4%) for ordinary ones, so this is not about frequency but about the remedy being unfollowable; their first call is genuinely bigger (p50 124k against 78k), which is what a continuation looks like. The section itself names what the trace is continuing, resolved through the `tool-use-id` the envelope quotes back: `LogRecordRepository.findToolCallByToolUseId` finds the dispatching `tool_result`, which lives in a **different trace** and so is not among this trace's own logs (**103 of 106** notification traces over 30 days carry an id, and all 103 resolve). Scoped to the session and bounded before the notification because `tool_use_id` carries no index — the `session.id` expression index does the narrowing, same literal-not-bind-param rule as `findLastAssistantResponseBefore`; measured 2.0 ms, 323 buffers, once per regenerate. **The dispatching call is the only thing pulled across the trace boundary, deliberately.** Merging the dispatching trace's spans was considered and rejected on measurement: for this trace that trace had **98 spans against its 6**, so the review would become a review of the other trace, and cost, cache reuse, token totals and revisit detection are all computed off the span list — merged, every headline figure would describe two traces while the page shows one. The template turns the section into two constraints rather than context to browse: a large starting context is expected and is not a finding, and the work being reported on happened elsewhere and must not be counted as this trace's own — the same failure mode the preceding-turn fence addresses, reached by a different route.

**Skills are read from `skill_activated`, not from `skillEventName`.** The two are different signals for different questions: `skillEventName` (`api_request`) is stamped on every model call made *while* a skill runs, which is why the markdown report has to de-duplicate it per prompt to count invocations; `skill_activated` fires exactly once per activation and carries `skill.name`, `skill.source` (`projectSettings` / `bundled`) and `invocation_trigger` (`user-slash` / `claude-proactive` / `nested-skill`) together. For "which skill drove this trace, and may the reader edit it" — the two facts the Apply-this target depends on — that is the exact signal, and it needs no de-duplication pass. The prompt's "Skills that ran" section names each one and **states that the skill's instructions are not included**, so a finding about a skill has to rest on what the calls show rather than on guessing at its contents. Note `claude-proactive` and `nested-skill` activations leave a real human prompt intact: only a `command_name` on the `user_prompt` drops the request half, not the mere presence of a skill. Relatedly, **never put example wording in the instructions**: an earlier template offered `"not sure if" / "maybe" / "some kind of"` as illustrations of hedging and the model quoted them back as though they came from the user's prompt.

The review judges three things — agent execution quality (tool selection, redundancy/thrash, error and rejection recovery, model-call proportionality, ask-vs-delivered), request quality (unnamed targets, ambiguity that cost work, drift), and cost/time/context (what drove the spend, where the time went, cache reuse, whether the request belonged in this session) — and answers in two sections, "What went wrong" (at most five bullets, each ending in a `Fix:`) and "Apply this" (the three lines above), plus a third, "What went well", on the minority of traces that clear a verified positive's bar (see the `Went well:` paragraph below). A trace with no `user_prompt` record — or one whose prompt is a `<task-notification>` envelope or a slash command — drops **only** the request half, since judging execution and spend needs no prompt to compare against; its `Better wording:` line is then `None`. **The overview is no longer marked "do not repeat these numbers back".** That instruction was there to stop a small model narrating figures instead of judging them, but it also fenced off the only data that answers "what drove the cost" — so the rule became "never restate a number on its own; a figure earns its place as the evidence for a change", and section C names the four questions those figures are for. The purge (`SystemService`/`SystemRepository`) has a fourth delete for `trace_analyses`, not FK-enforceable (`spans.trace_id` isn't unique): it runs unconditionally, immediately after the spans delete in the same transaction, deleting any row whose trace no longer has a surviving span — also reflected in the purge preview's per-table estimate and the Settings page's `deletedByTable` map.
- `otlp/` — the OTLP ingest slice, with its own sub-packages: `otlp/controller` (`OtlpLogController` / `OtlpMetricController` / `OtlpTraceController` accept `application/x-protobuf` on `POST /v1/logs`, `/v1/metrics`, `/v1/traces`), `otlp/mapper` (`OtlpLogMapper` / `OtlpMetricMapper` / `OtlpTraceMapper` — `@Component`s, not MapStruct — translate OTLP proto into `*Entity` rows including the attribute jsonb maps), and `otlp/service` (`OtlpLogService` / `OtlpMetricService` / `OtlpTraceService` write paths).
- `entity/` — JPA entities (`LogRecordEntity`, `MetricPointEntity`, `SpanEntity`). Attribute payloads use `@JdbcTypeCode(SqlTypes.JSON)` with `columnDefinition = "jsonb"` and a `Map<String, Object>` field.
- `repository/` — Spring Data JPA. Cross-row aggregations are native SQL (`@Query(..., nativeQuery = true)`); simple JPQL stays in repositories that don't need jsonb operators or window functions. `SystemRepository` is the exception to the one-repository-per-table shape: it owns no table, extends the bare `Repository<LogRecordEntity, Long>` marker (the entity is only a managed-type anchor for the proxy — no CRUD is exposed), and hosts the `pg_catalog` / `flyway_schema_history` / cross-table queries behind `/api/system`. Keeping it on Spring Data rather than introducing `JdbcTemplate` is deliberate: the backend has exactly one data-access idiom and is worth keeping that way.
- `service/` — `LogService` / `MetricService` / `MetricSeriesService` / `TraceService` / `TraceExplorerService` are `@Transactional(readOnly = true)` and own the parsing/cursor/range logic for dashboard endpoints; `ReportService` renders the markdown report from a Mustache template. The package also holds stateless helpers shared across those services — `PageBounds` (result-size clamping, see Data below), `HistogramBucketing` (bucket-width ladder walk for the Logs and Traces histograms; each page passes its own ladder), `BoundedEditDistance` (near-miss path matching for the report). Reuse them rather than re-extracting a second copy.
- `controller/` — per-domain REST controllers for the React app under `/api`: `LogsController`, `MetricsController`, `SessionController`, `ToolActivityController`, `TracesController`; `ReportController` serves the markdown report; `SystemController` serves the Settings page's operational diagnostics (storage, ingest health, build/schema, effective configuration, retention preview) — the only controller that takes no time window, since its figures describe the database as it stands, and the only one with a write: `DELETE /api/system/telemetry` is the sole endpoint in the application that deletes data. It requires an explicit confirmation phrase re-checked in `SystemService`, and `ApiExceptionHandler` maps the resulting `IllegalArgumentException` to a 400 so a refusal reads as declined rather than failed. `ApiExceptionHandler` (`@RestControllerAdvice`) maps bare-`@RequestParam` `ConstraintViolationException`s to 400 (class-level `@Validated` throws them raw, which would otherwise surface as 500s). The package also holds one non-controller `@Component`: `TraceAnalysisSseStreamer`, which runs a trace analysis on a bounded background pool and narrates it as Server-Sent Events for `POST /api/traces/{traceId}/analysis/stream`. It lives here rather than in `service/` on purpose — `SseEmitter`, event names and delta coalescing are HTTP shaping, and a service returning an `SseEmitter` would be the leak; the controller keeps its thin-dispatch shape. Four things about it are load-bearing. **Failures end the stream with a `failed` event and a normal close, never `completeWithError`**: the response is committed at 200 long before the model call, so there is no status left to fail with, and an errored close reaches the browser as a bare connection fault — throwing away exactly the user-facing message `OllamaUnavailableException` exists to carry. An unknown trace id (a 404 on the plain POST) travels the same way. **The emitter timeout is derived from `ollama.read-timeout` plus margin**, not left to the container's async default (commonly 30s, well inside a normal run). **A disconnected client stops the narration, not the run** — the analysis finishes and is stored, so reopening the dialog shows it, rather than throwing away a nearly-finished local inference run for a click that usually means "I'll check back later". And **`delta` events are coalesced** (120 characters or 200ms, whichever first) because a 7B model emits a token every few milliseconds and one frame each would be thousands of writes and React renders for a panel that only needs to look alive. Event *sequencing* is behind a package-private `EventSink` seam so `TraceAnalysisSseStreamerTest` can assert it — including that a pending delta is flushed before the phase event that follows it — without standing up a servlet response; `TracesControllerTest` mocks the whole component, since what it produces is a stream fed from another thread and says nothing about the controller's own job.
- `validation/` — `@ValidDateRange` + `DateRangeValidator` cap custom `startTimestamp`/`endTimestamp` ranges at 30 days; any param object exposing the pair implements `DateRangeBounds` so the one constraint covers it (`TimeWindowParams` via record accessors, `TraceFilterParams` explicitly).
- `model/` — record DTOs (Lombok `@Data @Builder` on older shapes like `ToolCallCount` / `TraceSummary`); MapStruct mappers in `mapper/` (`spring` component model, `lombok-mapstruct-binding` keeps them compatible) handle entity → DTO mapping for `LogRecord` / `Span` / `EventRow`.
- `config/` — `TuningProperties` (overridable event/attribute/metric names), `TuningPropertyCatalog` (the authored grouping + descriptions + SQL-mirroring classification of all 63 of those properties, behind `/api/system/configuration`; a reflection test fails the build when a property is added without being classified), `OpenApiConfig`, `MustacheConfig`, `SinglePageApplicationConfig`.

## Naming

- **All variables — method parameters, fields, and locals defined inside methods — use full descriptive names.** Never single letters or two-letter abbreviations. Use `anyValue` not `v`, `keyValue` not `kv`, `hexBuilder` not `sb`, `byteValue` not `b`, `request` not `req`. This rule applies to enhanced-for loop variables (`for (byte byteValue : bytes)`), not just declarations.
- Short names are allowed **only** in: lambda parameters, generic type parameters (`T`, `K`, `V`), standard index loops (`i`, `j`, `k`), and `e` in `catch (SomeException e)`.
- Prefer expressive names over abbreviations everywhere else: `throughputBars` over `bars`, `stepDetails` over `details`.

## Java style

- Java 21, `--release 21`. Don't lower the source level.
- Prefer `MediaType.APPLICATION_*` / `APPLICATION_*_VALUE` constants over string literals like `"application/x-protobuf"`.
- **Extract string literals defined inside methods as `private static final String` constants** at the top of the class — format specifiers (`HEX_BYTE_FORMAT = "%02x"`), header names, attribute keys, magic values, etc. Carve-out: one-off `log.*` and exception messages stay inline (extracting them adds noise without payoff).
- **Extract numeric literals defined inside methods as `private static final` constants whenever the number carries domain meaning** — conversion factors (`NANOS_PER_SECOND = 1_000_000_000L`), per-unit counts (`HEX_CHARS_PER_BYTE = 2`), thresholds, timeouts, sizes, ports, retry counts, etc. Small values like `2` are NOT exempt when they mean something specific. Carve-outs (stay inline): `0`/`1`/`-1` as identities, bit masks like `0xff`, generic index/loop arithmetic, test fixture data, and counts that are obvious from immediate context (`new ArrayList<>(events.size())`).
- Records (not Lombok-annotated classes) for new response DTOs; the legacy `@Data @Builder` shape stays for `ToolCallCount`, `TraceSummary`, etc. until they're touched for other reasons.
- Lombok + MapStruct are both on the annotation-processor path; new mappers use `@Mapper(componentModel = "spring")`.
- Checkstyle runs in the `validate` phase and fails the build. Max line length is 140; tabs are forbidden; `NeedBraces` is enforced (every `if`/`else`/`for`/`while` body wrapped, even one-liners).

## Web layer

- **Thin controllers.** Controllers dispatch to services and shape the HTTP response (headers, status, content-type) — no parsing, no cursor math, no validation logic. Validation is declarative: shared query params bind to `@Valid @ModelAttribute` param objects (`TimeWindowParams`, `TraceFilterParams`, …) carrying Bean Validation constraints like `@ValidDateRange`; `ApiExceptionHandler` turns bare-`@RequestParam` constraint violations into 400s. The dual-window endpoints follow a single shape: `if (startTimestamp != null && endTimestamp != null) return service.xxxInRange(start, end); return service.xxx(minutes);`. Mirror this pattern on every new dashboard endpoint so the frontend can always pick either window form.
- Annotate new endpoints with `@Tag` / `@Operation` (and `@ApiResponses` with concrete `@Schema`) so springdoc OpenAPI stays useful for the React client.
- When both Spring's `@RequestBody` and Swagger's `@RequestBody` are needed, import Spring's and fully-qualify Swagger's (it's documentation metadata, used less in code).
- Don't return JPA entities from controllers — map to a record (or the legacy `@Data` DTO) through MapStruct first.
- OTLP ingest controllers consume `application/x-protobuf` and respond with the matching `ExportXxxServiceResponse` protobuf body, returning `400` with a `partialSuccess.errorMessage` set on `InvalidProtocolBufferException`.
- **The backend also serves the SPA.** `SinglePageApplicationConfig` registers a `/**` resource handler over `spring.web.resources.static-locations` (the released image points that at the Vite bundle it copied in beside the jar; a plain `spring-boot:run` keeps the classpath defaults and serves nothing). Unresolved extension-less paths fall back to `index.html` so React Router's history-mode URLs work; paths with a file extension, and anything under the `SERVER_ROUTED_PREFIXES` list, stay 404 rather than answering a missing asset with HTML. **Adding a server-side route outside `/api` means adding its prefix to that list** — otherwise a mistyped URL under it returns the SPA instead of a 404.

## Data

- **Column names for ad-hoc SQL — read this before querying the database by hand.** The three signal
  tables do not share a time column name and none of them is called `timestamp` everywhere, which is
  what every hand-written investigative query gets wrong. `log_records`: `timestamp`,
  `observed_timestamp`, `received_at`, `body`, `trace_id`, `span_id`, `attributes`,
  `derived_severity`, `event_name`, `tool_name`. `spans`: **`start_timestamp` / `end_timestamp`**
  (never `start_time`, `timestamp`, or the OTLP wire name `start_time_unix_nano`), `duration_nanos`,
  `trace_id`, `span_id`, `parent_span_id`, `name`, `kind`, `status_code`, `attributes`, `events`.
  `metric_points`: `timestamp`, `start_timestamp`, `value_double`, `value_long`, `value_delta`,
  `stream_id`, `session_id`, `metric_name`, `attributes`. `trace_analyses`: **`analysis_text`** (not
  `analysis`) and **`generated_at`** (not `updated_at` or `timestamp`), plus `summary`, `model`,
  `last_span_end_timestamp`. A tool call's own execution time is not a column at all — it is
  `attributes ->> 'duration_ms'` on the `tool_result` log, while `spans.duration_nanos` includes time
  blocked on user approval. When a name isn't on this list, read it out of
  `information_schema.columns` in one query rather than guessing per statement.
- **Schema lives in Flyway migrations** under `src/main/resources/db/migration/` (`V1__init.sql` is the base, `V2__attribute_indexes.sql` adds the GIN indexes). `spring.jpa.hibernate.ddl-auto=validate` — Hibernate will fail startup if the entity model and DB drift, so every schema change goes through a new `V{n}__*.sql` migration.
- **Attribute payloads stay in `jsonb` columns** (`attributes`, `resource_attributes`, `scope_attributes`, plus `events` on spans); use the existing `@JdbcTypeCode(SqlTypes.JSON)` + `Map<String, Object>` converter pattern rather than flattening into columns. Index containment-style filters with `USING gin (attributes jsonb_path_ops)`.
- **Native SQL** is the norm in repositories — JPQL has no `jsonb_each_text`, `date_bin`, `percentile_cont`, or window-function support, and almost every aggregation needs at least one of them. Always parameterize values with `@Param` (no string concatenation into the query).
- **Range-and-fallback query pattern.** Repositories take an explicit `(Instant start, Instant end)` range; the service resolves the `?minutes=` form into `now - minutes .. now` and calls the same range method (`MetricPointRepository` and `SpanRepository` are fully consolidated this way; `LogRecordRepository` still carries some `aggregateXxx(..., Instant since)` / `aggregateXxxInRange(...)` pairs). Repositories that also serve the grid filters use a single method with `(CAST(:startTimestamp AS timestamptz) IS NULL OR timestamp >= :startTimestamp) AND (... endTimestamp ...)` so empty/one-sided/two-sided bounds all flow through one query.
- **Cumulative-counter deltas are precomputed at ingest.** `claude_code.*` counters (tokens, cost, active time) are cumulative and re-emitted per stream, where a stream's identity is the FULL attribute set (`query_source` / `agent.name` matter). `metric_points.stream_id` is a stored generated md5 of `metric_name` + attributes; `value_delta` is the reset-aware per-row increment, computed per ingest batch by `OtlpMetricService` (backfilled by `V11`). Every token/cost/active-time/session rollup reads `SUM(value_delta)` — never a plain SUM over the raw value columns, a read-time `LAG`, or bucket-`MAX`.
- **`metric_points.session_id` is a stored generated column, not a raw jsonb read.** `V18` materializes `attributes ->> 'session.id'` into a real `text` column (mirroring `V16`/`V17`'s `event_name`/`tool_name` on `log_records`, but for a different reason — `metric_points.attributes` is barely TOASTed, so this isn't a detoast fix). The window-scoped session CTEs in `MetricPointRepository` (`aggregateSessionSummaries`, `aggregateWorstCacheEfficiencySessions`, `aggregateSessionKpis`, `aggregateNewSessionsTrend`, plus the per-session lookups) filter on `metric_name` + `timestamp` and then need `session_id` per matched row; as an expression, that field can't ride in an index, so every row forced a heap-page visit even though the leading filter was already index-covered. `idx_metric_points_session_id_name_ts` (V13, formerly an expression index) and `idx_metric_points_name_ts` (V1, now `INCLUDE (session_id, value_delta, start_timestamp)`) both carry it as a real column so these queries serve as index-only scans. Only the literal `'session.id'` key was migrated — `findTopTokenRows`' `attributes ->> :sessionIdAttribute` stays a bind-param extraction, since `SESSION_ID_ATTRIBUTE` is shared with `SpanRepository` call sites outside this table.
- **`log_records.session_id` is a stored generated column too (`V30`), read so far by the purge queries and by `LogRecordRepository.aggregateFirstUserPromptsForSessions`.** Same `attributes ->> 'session.id'` materialization as V18, but for V16/V17's reason rather than V18's: `log_records` is 255 MB of heap against 7505 MB of TOAST, so reading one key detoasts ~11 KB per row. Measured three ways over the same 210k rows — `count(*)` 19 ms, `GROUP BY event_name` (a real column) 90 ms, `GROUP BY attributes ->> 'session.id'` **9144 ms**. That is why `SystemRepository.DORMANT_SESSION_IDS_SUBQUERY`'s log leg cost 10937 ms of a 12549 ms dormant-session computation (metric leg 1409 ms, span leg 193 ms) and pushed the purge preview past its raised 60s timeout 20 times, so **retention never ran and every other query got slower as the tables grew**. **`idx_log_records_session_id_ts` (the V3 expression index) is NOT a substitute and was measured failing twice**: the old `jsonb_exists()` filter isn't index-expressible so the planner discarded it, and rewriting the filter to `IS NOT NULL` still chose a seq scan (7845 ms) or, forced, a plain Index Scan — not index-only — at 12246 ms, detoasting one row at a time. **V30 deliberately keeps that expression index and moves only the purge queries onto the column**, because dropping it would strand the ~40 other callsites that extract this key (LogRecordRepository's per-session lookups, SpanRepository's 15 correlated session legs, and the two queries whose comments pin them to it by name) — exactly the trap V16 set and V19 had to clean up. Migrating those and then dropping the expression index is a V19-shaped follow-up, not done here. **The one non-purge query on the column is the Cost page's first-user-prompt lookup, and it is worth reading as the pattern for migrating the rest**: the fix there was not only swapping the expression for the column but declining to reuse `aggregateSessionCounts` at all. That query is deliberately unwindowed, matches every `event_name`, and reads three jsonb keys per row, so borrowing it for its `firstUserPrompt` column alone — which `CostService` and `MetricService.worstCacheEfficiencySessions` both did — made a 10-session lookup visit every log record those sessions ever emitted: **3544 ms and 421K buffers, against 18 ms and 573 for the purpose-built `aggregateFirstUserPromptsForSessions`**, byte-identical output on live data, and 85% of the whole `/api/cost/breakdown` latency. `MetricService`'s copy is unchanged and still pays it. A cheap column is not a substitute for asking the narrower question. **`spans` keeps the jsonb extraction** (193 ms; 169 MB heap against 48 MB TOAST). One semantic change rode along: the purge's sessionless branch now tests `session_id IS NULL` instead of `NOT jsonb_exists(...)`, which differ only for a key present with a JSON *null* value — a row the old form matched in neither branch and could never purge at any cutoff. 0 such rows exist on either table, and `metric_points` has read it this way since V18.
- **Streams are never retired, so "emitted recently" does NOT mean "active recently".** Claude Code's exporter keeps every metric stream it has ever created alive for the life of the process, re-emitting each cumulative counter once a minute at an unchanged value long after the session that produced it ended. Measured on the live database, 98.9% of all `claude_code.cost.usage` / `claude_code.active_time.total` points are such zero-delta re-exports, and sessions two days dead were still emitting them in the current minute. **Any query that decides membership, recency, or "is this thing live" by the presence of a row in a time window is wrong** — it must test `value_delta IS DISTINCT FROM 0` instead. This is distinct from the rollup rule below: `SUM(value_delta)` already gives the right *number* (ghosts contribute 0), which is precisely why the bug hides — the totals look correct while the row set and its timestamps are badly wrong. `MetricPointRepository.aggregateSessionSummaries` / `aggregateSessionKpis` / `aggregateNewSessionsTrend` carry the filter; a session's true start is `MIN(start_timestamp)` (when the stream opened, ~45s before its first emission) and its last activity is the newest timestamp carrying an increment. **There is a second, costlier way to get this wrong: reading the ghosts even where they cannot change the answer.** Only **46,995 of 8,586,064** `metric_points` rows (0.55%) carry a non-zero delta, so a correlated lateral that omits the filter reads ~180x the rows it needs — and `aggregateSessionSummaries` ran three of them per session, for every session in the window, *before* its `ORDER BY`/`LIMIT` could apply (every sort column but `session_id` is lateral-computed). That is 585 lateral executions for a 25-row page, ~1.9M buffers, ~15 GB — and it **timed out outright** on the live database at 15,424 ms against the pooled 15 s `statement_timeout`, which is a page that fails rather than a page that is slow. **The fix is an index, not just a filter**, and the distinction is the lesson: `value_delta` rides the older indexes only as an `INCLUDE` payload, never as a key, so adding the filter alone applied it *after* the heap fetch and bought 15,424 → 12,978 ms with the heap blocks unmoved. `V32`'s partial indexes make the ghosts unreachable instead of discarded — 15,424 ms → **18.9 ms**, buffers 1,938,070 → 15,097 — and cost 5.8 MB + 3.0 MB against an 8.7 GB table, because a partial index on 0.55% of a table is nearly free. Two traps V32's own header documents at length and worth knowing before touching that query: the `meta` lateral **must not** get the non-zero filter (`session.count` heartbeats are overwhelmingly zero-delta, and a `start_type=resume` stream emits only that metric — see [[project_resume_sessions_are_heartbeat_hosts]]), and it needs the `COALESCE(start_timestamp, timestamp)` *expression* as an index key to match its own `ORDER BY ... LIMIT 1`, or it sorts ~1,121 rows per session to take one. Also expect the cost/active sums to shift in their last bit or two: `double precision` addition is not associative and the index changes row order, measured at max 2.8e-14 USD (~1 ULP) with the window total unchanged. That is not a defect to chase. **The Trend Report was the same bug a third time, and it is the clearest statement of why `SUM(value_delta)` being correct is what makes this dangerous.** Its four `metric_points` aggregations (`aggregateMetricsTotalsCombined`, `aggregateMetricsSparklinesCombined`, `aggregateTokenTypeSparklinesCombined`, `aggregateSessionCountAndDurationCurrentAndPrior`) summed `value_delta` without filtering it, so every figure on the page was right while the scans read ~180x the rows they needed: `/api/trends/cost` **9.52 s** and `/api/trends/token-efficiency` **11.96 s**, against **0.12 s** for `/api/trends/reliability`, which reads `log_records` and never touches this table — that contrast is the tell. `V33` adds the companion index to V32's, keyed `(metric_name, timestamp)` rather than leading on `session_id`, because these queries scan a metric over a window instead of looking a session up by id: **V32's index cannot serve them**, and a second access path needs a second partial index (5.2 MB) rather than a wider shared one. With the filters: the totals query 6828 → 194 ms, the sparklines query 2785 → 49 ms. **Two rules fall out of this for any new query on this table.** Any `SUM(value_delta)` scan should carry `value_delta IS DISTINCT FROM 0` as a matter of course — it cannot change the sum and it is the difference between an index-only scan and reading the whole table. And a `GROUP BY` leg that gains the filter can now **omit a group** where it used to emit an explicit `0` (a token type whose every row in the window is a ghost), so the consuming service must default a missing group to zero rather than assume every group is present; `TrendService#queryMetricsTotalsCombined` already does, by initialising its accumulators to `0.0`. Note also that `/cost` and `/token-efficiency` deliberately **duplicate** the same three queries (both call `queryMetricsTotalsCombined` + `querySessionTotals` + `queryMetricsSparklinesCombined`), so the page runs each twice concurrently — acceptable now that each is tens of milliseconds, but it is why splitting these endpoints further would have made the page slower, not faster.
- **The retention purge deletes whole sessions, never rows.** `session.id` sits in the `attributes` jsonb of `log_records`, `metric_points`, and `spans` alike (100% coverage on live data), which is what makes this possible: `SystemRepository.DORMANT_SESSION_IDS_SUBQUERY` computes every session whose last activity *anywhere* — logs, tokens, or traces — is older than the cutoff, and every purge query (`purgeLogRecords`/`purgeMetricPoints`/`purgeSpans`, plus `findPurgeEstimates`) gates on that same set. A row-age-only delete would silently split a session straddling the cutoff — its early turns gone, recent ones kept, lifetime cost permanently understated. Measured on the live database: 0 sessions straddle the default 30-day window, 21 straddle a 7-day one, accounting for 604k rows a naive delete would have partially removed. A sessionless row (unobserved on live data but not guaranteed by the schema) falls back to plain `timestamp < cutoff` deletion — the pre-session-gating behavior.
- **Every purge/preview candidate scan also carries a redundant `timestamp < cutoff` (or `start_timestamp`) guard alongside the dormant-session membership check**, purely so the planner can apply it as a leading index-scan restriction before paying for the `IN` lookup or, on `metric_points`, the correlated `EXISTS`. It changes no result — provably so: a session is only dormant once `max(last_seen)` (the max across all three signals' own per-session maxes) is `< cutoff`, so every row belonging to that session in every table already has `timestamp <= that table's own per-session max <= max(last_seen) < cutoff`. `SystemRepository.DORMANT_SESSION_IDS_SUBQUERY`'s javadoc carries the full argument; `SystemService`'s rendered-SQL mirrors (`SESSION_GATED_DELETE_FORMAT`, `METRIC_POINTS_DELETE_FORMAT`, `PURGE_SCRIPT_HEADER`) were updated in lockstep, and `SystemPurgeIntegrationTest`/`SystemQueryIntegrationTest` (22 tests) still pass unchanged, since the row set purge/preview computes is identical — only the plan Postgres picks to get there differs.
- **Inside a purged session, `metric_points` additionally keeps each stream's newest row.** `value_delta` is computed at ingest against the previous row in the same stream and `COALESCE`s to zero when there is none, so even a session judged dormant and eligible for deletion would spike its own counters if it turned out not to be finished after all: `SystemRepository.purgeMetricPoints`'s `EXISTS` clause runs unconditionally, not gated on session dormancy — "no activity anywhere for a full retention window" is strong evidence the process exited (Claude Code re-emits every counter roughly once a minute for its life) but not a proof of it. This is a defensive assumption, not a confirmed mechanism: no concrete way for a purged `session.id` to re-emit has been verified — it is specifically **not** known to be `claude --resume`, which a live-database investigation of `session.count` streams found mints a disjoint, never-before-seen session id for the heartbeat it emits (a genuinely new stream has nothing to protect; what session id ongoing interactive work uses after a real resume is unverified) — but none has been ruled out either, so the marker closes the question rather than trusts the assumption. Costs ~1 row per dormant stream (~2,200 of 2.2M at the live database's default window). The preview's `preservedRows`, the endpoint's DELETE, and the copyable SQL the UI hands the operator all run the identical predicate — a naive delete pasted into psql would corrupt the same data or split a session. `SystemPurgeIntegrationTest` has one test per guarantee: `purgeNeverTouchesASessionThatIsStillActiveInAnySignal` and `purgeGatesOnActivityAcrossAllThreeSignalsNotJustOneTable` for whole-session gating; `purgeKeepsALiveStreamsPredecessorSoTheNextEmissionIsNotASpike` and `purgeStillKeepsAStreamMarkerInsideAFullyDormantSession` for the stream marker — each purges, re-ingests, and asserts the resulting delta is the increment rather than the whole counter.
- **The purge's dormancy window and Claude Code's own `cleanupPeriodDays` are unrelated settings.** `cleanupPeriodDays` (default 30) controls how long Claude Code keeps a session's local transcript resumable on the user's machine; it is never emitted via OTLP, so this application has no way to know it. If an operator sets the dashboard's retention window shorter than their `cleanupPeriodDays`, a session can still be locally resumable in Claude Code after its telemetry — prompt timeline, tool calls, cost breakdown — has already been purged from `log_records` and `spans`. Resuming then shows the conversation continuing normally, but the Sessions/Logs/Traces pages show that session's history as if it only started at the resume point. There is no code-level fix for this — the two settings live in different systems — so the guidance is operational: keep the dashboard's retention window at least as long as `cleanupPeriodDays` if session continuity in the dashboard matters. The purge dialog and README both say so.
- **Planner statistics on this schema are not trustworthy; count exactly.** `pg_class.reltuples` reports `-1` for a freshly migrated `flyway_schema_history`, and `pg_stat_user_tables.n_live_tup` was measured reporting **6** rows for a table holding **19**. `SystemRepository` therefore uses exact `COUNT(*)` everywhere, which costs 250 ms on the 4.6M-row `metric_points` (an index-only scan) — comfortably inside the 15s `statement_timeout`. Don't "optimize" those into estimates. Two related measurements worth not rediscovering: **`received_at` carries no index on any of the three tables**, so `MAX(received_at)` is a 349 ms sequential scan and bounding it by the indexed `timestamp` does *not* help (a 7-day bound covers ~25% of the table and still plans a seq scan) — read it off the newest row by index order instead (`ORDER BY timestamp DESC, id DESC LIMIT 1`, 0.026 ms); and **`COUNT(DISTINCT stream_id)` (668 ms) is the cheap proxy for metric-series cardinality**, where `/api/metrics/catalog`'s `COUNT(DISTINCT attributes)` over the jsonb payload measured 2188 ms for a single 7-day window.
- **`UNION ALL` legs come back in whatever order Postgres likes.** `SystemRepository.findIngestHealth` returned its legs traces-logs-metrics against the live database while a small test container returned them in written order; its trailing `ORDER BY` is load-bearing, not decoration. Any multi-leg query whose row order reaches the UI needs one.
- **Result-size clamps.** `service/PageBounds` is the single shared helper for cursor-limit / offset-page-size clamping and offset arithmetic — `LogService`, `TraceExplorerService`, and `MetricService` all clamp through `PageBounds.clampPageSize` / `PageBounds.computeOffset` against its `MAXIMUM_PAGE_SIZE` (500) ceiling so attacker-chosen sizes can't OOM or overflow the "+1 probe". Belt-and-braces below that, every pooled connection runs with `statement_timeout = 15s` (`hikari.connection-init-sql` in `application.yml`). Point any new list endpoint at `PageBounds` rather than copying the clamp again.
- **Prompt text lives only on log records, and correlates to traces by `trace_id`.** The raw user prompt is the `prompt` attribute of a `user_prompt` log record (`TuningProperties.promptAttribute` / `userPromptEventName`) — no span carries it. Claude Code stamps each of those logs with the `claude_code.interaction` root span's trace id in the top-level `log_records.trace_id` column, which is how `SessionSummary.firstUserPrompt` (per session) and `TraceSummary.firstUserPrompt` (per trace) resolve prompt text; `MetricService.worstCacheEfficiencySessions` reuses the same `LogRecordRepository.aggregateSessionCounts` query (keyed on the ranked session ids) to fill `SessionCacheEfficiency.firstUserPrompt` rather than writing a second aggregation. Whitespace-collapse and the 200-char preview truncation happen **in SQL** so services never hold untruncated prompt bodies. A null prompt is a normal outcome, not an error: the trace may not be rooted in a conversational turn, or prompt-body capture may have been disabled when it was recorded.
- **Only `api_request` log records carry a model.** `tool_result` rows have no `model` attribute at all, so any per-model split over tool calls has to be correlated, not read. `LogRecordRepository.aggregateToolInvocationsByInnerAttributeAndModelInRange` (the `subagent-usage` split) does it with a `LEFT JOIN LATERAL` back to the last `api_request` in the same `session.id` at or before the tool call, excluding rows that carry `agent.name` — those are turns from *inside* a subagent run, which interleave with the dispatching tool call and would otherwise shadow the dispatcher. Unmatched calls bucket under an `unknown` model rather than being dropped. `agent.name` itself is not a subagent identifier: Claude Code collapses project-local agents to `custom`. A dispatch carrying no `subagent_type` anywhere is credited to `TuningProperties.defaultSubagentType` (`general-purpose`) — that is the agent such a dispatch actually runs on, so an `unknown` identifier bucket there was under-reporting a real one (29 of 254 calls on the live database).
- **MCP tool calls are named differently on the two signals that carry them, and both needed fixing.** On `log_records` (`tool_result` / `tool_decision`), `tool_name` is the single constant `mcp_tool` for every server — the real server/tool identity lives in the `tool_parameters` JSON-**string** attribute, under `mcp_server_name` / `mcp_tool_name` (100% coverage on live data). On `spans` (`claude_code.tool`), `tool_name` is instead the prefixed raw form `mcp__<server>__<tool>` — proliferating into 19+ rows per server that need collapsing, the opposite problem. `LogRecordRepository.MCP_AWARE_TOOL_EXPRESSION` splits the log side back out to `mcp:<server>` rows (reused across the 14 log-backed aggregations that group on the tool dimension); `SpanRepository.aggregateToolLatency`/`InRange` collapse the span side with `starts_with()`/`split_part()` (never `LIKE` — a bare `_` is the `LIKE` single-character wildcard, so `LIKE 'mcp__%'` would match "mcp" plus any two characters plus anything). `/api/tool-activity/mcp-usage` and the report's "MCP servers" section deliberately read only the log side: report **log `duration_ms`** (execution only), never span duration, which includes time blocked on user approval — confirmed on live data, one tool measured p95 297s on spans against 8ms average execution in the log. `aggregateToolRepeats` and `findToolEventsForSession` are deliberately NOT split — see their own comments (the former's `(no scope)` drop, the latter documented in `SessionsPage/CLAUDE.md`).
- **A skill invocation is one prompt, not one `api_request`.** Claude Code stamps `skill.name` on *every* model call made while a skill runs, and the attribute propagates into subagents the skill spawns — which carry their own `prompt.id`, so deduplication alone does not exclude them. Counting those rows measures how chatty a skill is, not how often it ran: on the live database that inflated totals 1.7x-46x (`code-review` read 1467 against 11 real invocations) and reordered the ranking, since a skill that fans out to subagents outscored one invoked nearly twice as often. `LogRecordRepository.aggregateSkillInvocationsByModelInRange` therefore drops turns carrying `agentNameAttribute` and takes `DISTINCT ON (identifier, prompt_id)`, attributing each invocation to its **earliest** surviving turn so the per-model split still sums to the row total when one prompt spans models. Do not "fix" this by counting the `Skill` dispatcher's own `tool_result` rows instead — a skill invoked as a slash command never goes through that tool, and that population is ~7x smaller than the truth (10 rows across three months).
- **Configurable event/attribute names.** Dashboard aggregations are driven by `TuningProperties` (`tuning.*` in `application.yml`) — `toolEventName`, `toolAttribute`, `tokenUsageMetric`, etc. Defaults match Claude Code's emission shape. Don't hardcode `"tool_result"` / `"tool_name"` / `"claude_code.token.usage"` in queries or services; read them from `TuningProperties`.
- **Derived cost.** Trace and span cost are computed in SQL from the *reported* per-request figure, not estimated: the `span_costs` / `trace_costs` views (`V14`) sum `cost_usd` across the `api_request` log records Claude Code stamps with a trace id and, when the exporter provided one, a span id. `trace_costs` sums every trace-correlated request log (including ones with no span id) and is authoritative for a trace's total cost; `span_costs` groups the subset that also carries a span id, so it is a per-span **breakdown** of `trace_costs` that can sum to LESS than the trace's total — the two are NOT guaranteed equal, and nothing should filter `trace_costs` down to try to force them to be (that would drop real cost data). Trace-list queries fill `TraceSummary.totalCostUsd` (and the `sort=cost` keyset) with a `LEFT JOIN LATERAL` that re-runs `trace_costs`' predicates against `log_records` per trace rather than joining the view directly — Postgres can't push a window/`LIMIT` past the view's `GROUP BY`, so a plain join re-aggregates every `api_request` log in the table on every page regardless of window size (see `SpanRepository`'s Trace Explorer queries section for the measurements). `TraceService.spansForTrace` fills `Span.costUsd` with one grouped query per trace against `span_costs` (`SpanRepository.findSpanCostsForTrace`) rather than a per-row `@Formula` — the formula ran one correlated subquery per span on every trace-detail load, paid even by callers that never read cost. **The Sessions prompt timeline is trace-correlated** (`LogRecordRepository.findCostSplitByTraceIds` via `LogService.applyTraceCorrelatedActivity`) for any turn that has a trace, so a prompt's cost and the cost on the trace it links to are the same number — but only once per trace: several turns in a row can share one trace, and the trace's cost is billed to the earliest of them only (later turns sharing it are cleared to no cost), so the sum over a session's turns still equals the sum over its distinct traces rather than double-counting a shared one. Turns and traces with no correlated request log fall back to / stay at the counter-derived value (`claude_code.cost.usage`), which is also what per-session totals and KPIs still use. An earlier revision's token-price estimate was removed for running 2-3x off real spend; don't reintroduce a rate table on either side.
- **A turn's own trace-correlated cost is not the same query as `trace_costs`, on purpose.** `findCostSplitByTraceIds` recomputes the identical `SUM(cost_usd)` predicate directly against `log_records` rather than joining the `trace_costs` view, because it also needs a `root_ends` CTE (`spans` filtered to `parent_span_id IS NULL AND name LIKE 'claude_code.interaction%'`, `MAX(end_timestamp)` per trace) to split that total into `own` (billed before the trace's root span closed) and `background` (billed after) — the same total the view gives, plus a second column the view has no way to express. `findToolEventsSplitByTraceIds` mirrors this for tool-call counts. **Fixes a real bug, not a hypothetical one**: a fire-and-forget subagent dispatch (an `Agent` tool call whose own span closes in milliseconds) can keep issuing `api_request`/`tool_result` logs long after the turn that launched it ended — those logs get stamped with whichever `prompt.id` was current when they fired, not the dispatching turn's, so `LogService`'s exact per-request `REQUEST` attribution (joined on `prompt.id`) previously discarded the trace-correlated total entirely and could disagree with the trace detail page by an order of magnitude. Measured on the live database: 4.1% of traces in a 14-day window have request activity after their own root span closes, accounting for 22.6% of all spend in that window — not a rare edge case. `SessionPrompt.costUsd`/`.tools` are now always the turn's trace total (matching what `GET /api/traces/{traceId}/summary` reports for the same trace); `backgroundCostUsd`/`backgroundTools` isolate the post-root-span portion so the dashboard can show *why* a turn cost more than what happened while it was the active turn, not just that it did. **Postgres will not `GROUP BY` a repeated parameterized jsonb expression, even via its own `SELECT`-list alias** — confirmed directly against Postgres (`PREPARE`d, not just via Hibernate): two placeholders bound to the identical runtime string are still different `Param` nodes in the parse tree, so `GROUP BY` validity fails with "column ... must appear in the GROUP BY clause" even for a single occurrence grouped by its own alias. `findToolEventsSplitByTraceIds` works around this by materializing `attributes ->> :toolAttribute` into a plain column via a CTE before the outer `GROUP BY`, which needs no parameter-equivalence proof at all — reach for that shape rather than repeating a parameterized expression in `GROUP BY` anywhere else in this codebase.
- **Per-span effort is a correlation, not an attribute.** Claude Code never emits `effort` on a span -- only on the `api_request` log -- so the `span_efforts` view (`V15`) joins the two on the **`request_id`** attribute and `TraceService.spansForTrace` fills `Span.effort` from it with one grouped query per trace (`SpanRepository.findSpanEffortsForTrace`), the same shape `applySpanCosts` uses. The join key is deliberately NOT `span_id`: as V14 explains, request logs carry the span that was *active* when the request was issued (the interaction root, or a `tool.execution` span), never the `claude_code.llm_request` child that represents the call, so a `span_id` join would attach effort to the wrong span while looking correct. `request_id` is unique on both sides (14,055/14,055 llm_request spans; 14,047/14,047 api_request logs), and input/output token counts agree across all 13,999 joined rows -- the pairing is exact, not a nearest-match. Spans absent from the view keep a **null** effort and the service applies no default, because "not recorded" (~2% of recent calls, more in older data) and "ran at the default level" are different facts.
- **Telemetry collection starts 2026-05-22 — never measure anything over all time.** The first three days are ingest-bootstrap data (19 sessions; counters and `api_request` logs disagreeing by +146% in aggregate; six of the eleven sessions that have EVER diverged more than 2x), and because volume was tiny then and has grown since, that window still skews any query that sums or averages across the whole table. Default every investigative query to a recent window (14-30 days), and **bucket by week to confirm an effect persists before calling it systematic** — a single anomalous week dominating an all-time number is the signature of this trap. This is not hypothetical: an all-time read of exactly this data produced a three-phase plan to fix a "counters undercount by up to 80%" problem that does not exist (measured 2026-08-21, the two pipelines agree within ±4% on every token kind DB-wide, and no session has diverged more than 2x since 2026-07-17). Two related traps from the same episode: distinguish **"the label is absent" from "the traffic is missing"** — the two pipelines use disjoint `query_source` vocabularies (counters emit `main` / `auxiliary` / `subagent`, logs emit `sdk` / `agent:*` / `generate_session_title` / `compact` / `web_*`), so no counter row is ever labeled `sdk` even though it counts the same calls; and before blaming `value_delta` for an inflated counter, check `metric_points.start_timestamp` (OTLP's `start_time_unix_nano`) — a stream's first row legitimately carries its full cumulative value, and that is an overcount only if the series had been running well before the row's timestamp, which it essentially never has (740 of 752 recent `token.usage` streams open within two minutes of their own series start).
- **Two token/cost pipelines that do NOT reconcile.** `metric_points` (cumulative counters, read as `SUM(value_delta)`) and `api_request` log attributes (`input_tokens` / `output_tokens` / `cache_creation_tokens` / `cache_read_tokens` / `cost_usd`, exact per call) both describe spend, and they disagree by tens of percent in **both** directions on real data — dominated by cache-read tokens (one live session: 157.6M cache-read per-request vs 29.3M from the counter; the two pipelines also label `query_source` differently, `sdk` vs `main`). Partial log coverage explains the cases where the request side is lower; nothing yet explains the cases where it is higher. So: pick one source per figure, label which one a number came from, and never add, average, or diff them. The prompt timeline does this explicitly — `SessionPrompt.attribution` is `REQUEST` (summed from the turn's own `api_request` logs, joined on `prompt.id`) or `INTERVAL` (bucketed from counters by timestamp), decided **per turn**, so a session that gained event logging partway through reports each turn however it can be measured. A consequence worth knowing before filing a bug: a session row's `tokenBreakdown` no longer equals the sum of its turns' `tokens`. There is deliberately **no test asserting the two pipelines are approximately equal** — that assertion would fail against real data; `TokenTelemetryQueryIntegrationTest` instead pins the reconciliation that does hold, that a turn's rollup equals its own requests summed.
- **`prompt.id` is the exact turn↔request join key.** Both `user_prompt` and `api_request` logs carry it (verified at 1266/1266 and 13819/13822 rows), which is what lets per-turn rollups be a `GROUP BY` instead of a timestamp-interval bucketing that bills a slow response to whichever turn was open when it landed. `LogRecordRepository.aggregateApiRequestTurnsForSession` / `findApiRequestsForSession` are the query family; `effort` is absent on ~7% of `api_request` rows, so treat it as nullable rather than defaulting it.
- **Derived severity.** Log severity is computed, not taken from OTLP: the `derive_log_severity()` function (`V6`) feeds the stored generated `derived_severity` column (`V8`). The classification defaults are documented on `TuningProperties` and mirrored client-side by `severityOf` in `frontend/src/pages/LogsPage/logsApi.ts` — redefining the function requires a migration that also rebuilds the stored column, so change all three in lockstep.
